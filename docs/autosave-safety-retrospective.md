# 保存安全性改善の経緯（2026-03）

## 背景

- 課題は「通信中や通信失敗時に未保存フラグが早く下がると、離脱時警告が出ずにデータを失う可能性がある」ことだった。
- 初期案としては、localStorage などを使った広範なオフライン対策も検討した。

## 検討した案

### 1) 全ページで強いオフライン基盤を導入

- Inbox / Projects / Knowledge / Schedules すべてに永続下書きや再送キューを導入する案。
- 個人開発・単一ユーザー前提では実装と運用コストが高く、オーバースペックと判断。

### 2) 最小修正で `hasPendingChanges` の意味を厳密化

- `hasPendingChanges` は「保存成功が返るまで true」を原則にする。
- これにより、通信中・失敗中は beforeunload 警告が維持される。
- 大改修なしで「うっかり離脱によるロスト」を大きく減らせるため採用。

### 3) Schedules だけ localStorage を残す案

- Schedules でのみ、通信失敗や離脱時に localStorage バックアップを使う方針。
- 「古い draft が DB の最新データを上書きする」懸念が残った。

## 最終判断

- **localStorage は廃止**し、保存安全性は以下に統一する。
  - `hasPendingChanges` を保存成功時のみ解除
  - `beforeunload` と `visibilitychange` / `pagehide` / `freeze` でデバウンス待ち保存を flush
- これにより、ロジックを単純化しつつ、警告と保存タイミングの一貫性を優先する。

## 設計メモ

- この方針は「クラッシュ後の自動復元」よりも「古いローカルデータが正データを上書きするリスク回避」を重視したトレードオフ。
- 今後再び永続下書きを導入する場合は、最低でも以下を満たす必要がある。
  - バージョン比較（更新時刻・世代番号）
  - マージ競合ポリシーの明文化
  - 破棄条件と UI 通知の定義
