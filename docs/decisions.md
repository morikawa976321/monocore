# 設計判断の記録 — 面ごとに選んだことと理由

`docs/design.md` は「守る制約」と「未決」だけを持つ。ここは**個別の面・実装で選んだことと、その理由**を置く。廃止したものは現状(何を持たないか)だけを書く。Supabase の権限・migration・観測は `docs/database.md`。

## 面を足す・減らすときの判定(design.md 制約10の運用)

- 「使われ続けた」の観察判定が効くのは**新しい習慣を仮定する面**だけ。既存の習慣の置き場を移すだけの面には適用しない(`/news` は移設前から毎日読んでいたものの移設なので、判定対象になる不確実性が無い。2026-08-14)。
- 毎日でなくても、使う場面が具体的に特定できているなら足してよい(`/reports`:「電車内で確実に使う」2026-08-09)。読み取り専用の導出物は、使われなくなってもテーブルとページを消すだけで損失が出ない。過去に消えた面はすべて入力を伴う面だった。
- 反映が定時ジョブ(旧 taskbox の drain 枠など)でしか起きない非同期の面に人間の判断を通す経路を作るなら、**その往復が「セッションを開いて直接聞く」より速いことが成立条件**。成立しないなら読む専用にする(2026-08-11)。
- カードや行に分類軸(目標・タグ)を足さない。抱えられる数に見合わない分類は複雑性そのもの(2026-08-23)。
- 毎回少しずつ足す経路にある分量の規約は、散文で書いても守られない(300 字上限が制定後3週間で 14.6 倍になった)。機械判定できるなら投入の境界で弾くか切る(例: 廃止した `drain_runs` の要約上限は投入スクリプトで切り捨てていた)。
- 一覧の目的は網羅ではない。載せるかは「本人が待たれているか/再開の合図が近いか」で決め、「進行中か」では決めない。動いていない行が多いほど、動いた行が埋もれる。

## プロジェクト板は持たない(2026-09-11 廃止)

- `/projects`・`project_cards` テーブル・taskbox 側のカード生成を廃止し、テーブルも DROP 済み(migration `20260911202118`)。理由(本人): 利用頻度が落ち、半ば義務化していた。2026-07-17 の旧 projects 削除(「ほとんど見ていなかった」)に続き2度目。
- プロジェクトの背景・状況・進行中一覧は monocore に持たない。人間がやる期日ありのタスクは schedules に置く。

## Schedules

- 日別メモ欄(`schedule_day_notes`)は予定欄と併設する。PC(`sm` 以上)は横並びで予定:メモ = **3:2**(本人指定。50:50 案は採らず)、スマホは縦積み(幅 375px で横2分割は両方とも実用に耐えない)。競合制御は inboxes と同じ last-write-wins で、予定側の楽観ロック経路(`replace_schedules_for_day` + `schedule_day_revisions`)には触れない。`DayEntry` 型には入れず `useDayNotes` が `Map<dayKey, string>` で独立管理する(`text-format.ts` / `sync.ts` とその検査への波及をゼロにするため)。2026-08-05。
- テキストエリアの最低高は 40px(1行 24px + `py-2`)。数値の根拠は `src/components/schedules/DaySection.tsx` のコメント。
- 既定予定(`default_schedules`)は、画面が日を読み込む直前に `apply_default_schedules` で**実データとして書き込む**(本人の要望「UIから見たすべての日に自動で入っていてほしい」、2026-09-28)。表示時に重ねるだけの仮想方式は採らない: その日だけ消す・ずらすたびに例外の記録が要り、日を丸ごと置換する保存経路と噛み合わない。書き込み済みの (既定予定, 日) は `default_schedule_applications` に残すので、その日の既定予定を消しても復活しない。帰結として、既定予定の時刻を変えたり削除したりしても、**書き込み済みの日(読み込んだ範囲 = 概ね今日から2ヶ月先まで)には反映されない**。`effective_from` より前の日には入れない(過去方向の無限スクロールの停止条件と過去の記録を守るため)。追加・削除は monocore スキルの `defaults` コマンドから行い、画面には管理UIを持たない。
- 空の日を折りたたむ抜本策は採らない。スクロール長の真因は「空の日が空のまま場所を占めること」だが、折りたたみは「どの日にもすぐ書ける」性質を壊す。最低高の縮小はその緩和策。

## 空き時間の3色の帯(2026-10-07 新設)

本人の要望(2026-10-07):

> 1日の中でどれくらい空き時間があるかはスケジュールページにそのまま表示し、長期的な計画を立てるページを新設し、そちらでは上記の目標を入れられるようにしよう。

- **スケジュール画面の空き時間の機能は日カードの3色の帯だけ**(本人指定 2026-10-13: 「スケジュールページには空き時間を表示しないように修正して。また、上部の計画関連エリアも廃止。スケジュールページの計画関連の機能は3色バーのみとする」)。見出しの「空き」の数値とページ上部の目標の帯は同日に外した。
- **帯は見出し行の中に置き、カードの高さを増やさない**(上の最低高と同じ理由。60日分で約1,000px 伸びる)。スマホは帯を出さない。帯は睡眠・非自由・自由の3色(本人指定 2026-10-07)。PC ではバッジ・元に戻すボタンの幅を常に確保し、帯の長さが日ごとに変わらないようにする(同)。
- **予定は起床を除いて開始と終了を必須にする**(本人指定 2026-10-07)。起床の行は「起床」を語として含む行(前後が行端か空白。`isWakeActivity`。「起床時刻の見直し」「起床。」は起床の行ではない。本人選択 2026-10-18)で、空き時間の計算と同じ判定を使う。終了の無い行・終了が開始より前の行・時刻の無い行がある日は、見出しに Invalid format のバッジを出し(直す行はバッジのツールチップ。本文の上に警告文の行は出さない、本人指定 2026-10-07)、**その日は保存しない**(`findDayContentIssues` → `useSchedules.saveDay`。dirty のまま残し、直した編集で保存する。通信しないので再試行は起きない)。日付を跨ぐ予定は日ごとに分けて書く。規則を入れる前に保存された開始だけの行は、計算では数えない。
- **自由時間の数え方**(`src/lib/schedules/free-time.ts`。本人指定 2026-10-07、睡眠の数え方は 2026-10-18 改訂。形式的な定義・守る性質・テストの方針は `docs/free-time-model.md` で、規則を変えるときはその §2 の定義を先に直す): **スケジュール画面の予定を正とし、帯と自由時間はそこから導出する**。時間は日をまたいで連続しているとみなし(「日単位で考える必要がない」)、睡眠 = 消灯の予定が終わってから次の起床まで。起床・消灯の行は「起床」「消灯」を語として含む行(睡眠と同じ規則。部分一致だった間は「起床時刻の見直し」「消灯前の片付け」のような予定が睡眠の境目を動かしていた。本人選択 2026-10-18、`docs/free-time-model.md` カード2)。起床が続いたり消灯が続いたりしたら2つ目以降は境目として無視する(本人の案)。非自由 = 起きている間の予定の時間(消灯の予定を含む)と、起床から最初の予定までの身支度(最大2時間。起床の行が `0700-1200 起床` のように範囲を持つ日はその範囲)。身支度は最初の予定で終わるので、朝の2時間の中に短い予定を足すと予定の後が自由になり、自由時間が増える(`0700 起床` の日に `0730-0740` の予定を足すと 13時間 → 14時間20分。本人がこの帰結を確認し、常に2時間にはしない。2026-10-18、`docs/free-time-model.md` カード1)。境目にならない起床(前日から起きたままの日の起床)にも身支度を付ける(同、カード5)。自由 = それ以外の起きている時間。「睡眠」を語として含む予定(昼寝など)は帯で睡眠の色に塗る(境目は動かさない。自由時間の数は変わらない)。終了の `2359` は24時として数える。**既定の 0700 起床・2200-2300 消灯で補うのは、スケジュール画面でまだ読み込んでいない日(既定予定を書き込んだ記録 `default_schedule_applications` の無い日)だけ**で、読み込んだ日は行が無ければ本人が消したものとして補わない(全部消した日は前の日の状態が続く。前夜に消灯していれば次の起床まで丸ごと眠っていて、前夜に消灯が無ければ24時間起きている。本人選択 2026-10-18、`docs/free-time-model.md` カード3)。スケジュール画面も記録で判定し、既定予定の `effective_from` より前の過去の日(記録が残らない)は未読込として補う(本人選択 2026-10-18、`docs/free-time-model.md` カード4。それまでは画面に出す日をすべて読み込んだ日として扱っていたので、消灯の行が無い過去の日は眠らず、その状態が既定予定の最初の日の朝まで及んでいた)。改訂のきっかけは日をまたいだ就寝(10/18 の `0000-0300 消灯`)で、日ごとに区切る旧方式では前日の夜が既定の 23時からの睡眠になり、当日の 0〜3時も睡眠として塗られていた。予定の種類(受け取り等)は区別しない。最長の塊・まとまった枠・生活時間の差し引きは、本人が不要と判断して外した(「純粋な空き時間だけ管理できればいい」)。
- **目標(`plan_goals`)と締切までの時間の累計グラフは持たない**(2026-10-23 廃止、テーブルも DROP 済み。migration `20261023180000`)。本人の指示は「目標と累計グラフを削除して。3色の帯は残す。plan_goals も DROP してよい」。本人の発言は「時間を把握して割り当てていくという機能がいまいち使いずらくてほとんど使っていない」で、同じ作業を対話セッションで直接行ったほうは有用だったと述べた。目標は 2026-10-08〜13 に14件まで入り、最後の更新は 2026-10-13、2026-10-20 以降の定期バックアップでは0件だった(design.md 制約10の「使われ続けた」を満たさなかった)。

## /reports ミラー

- 方式は読み取り専用ミラー。読む場面はラップトップがスリープ中の電車・ベッドなので 24/7 可用性が必須で、Tailscale + ローカル HTTP はスリープで死に、GitHub private repo は reports 側の規約が禁止している。閲覧専用なので双方向同期の難所(schedules が日単位版管理で払ったコスト)が丸ごと要らない。2026-08-09。
- 全件同期(ホワイトリストで選別しない)。reports のコミットと upsert をセットで走らせ(`mf/ops/sync-reports.ps1`)、ミラーが腐らないようにする。
- 同期は「集合の一致」であって upsert ではない(ローカルに無い slug は delete。`scripts/upsert-reports.mjs`)。upsert だけだと削除・archive 移動・リネームがミラーに残り続け、「ローカルが正」が破れる。
- 導出物は単一形式でのみ持つ(md と HTML の二重保持をしない)。片方を捨てて失う機能は**列を足さず別の手段で代替**する(本文の全文検索はタイトルと見出しのみに絞り、本文内はブラウザのページ内検索に任せる)。容量は律速ではない(reports 約 1MB/月、無料枠 500MB、2KB 超の text は TOAST が圧縮)。この2原則は容量対策ではなく正しさのために採る。
- `_index.md`・`CLAUDE.md`・`archive/` は同期対象外。索引にだけ書いた注記(「この結論は死んでいる」等)はスマホから本文を開く読み手に届かない。そういう警告は本文の冒頭に書く。

## /news と scraper

- 保持は 8 日で物理削除。DB に蓄積して表示側だけ直近 N 日に絞る案は採らなかった(2026-08-14)。
- scraper は Python のまま置き、node へ書き直さない。統合で得たいもの(フォルダをなくす・スキーマとライターを同じコミットに乗せる)は言語に依存しない。書き直しの対価は、既に直したバグ(エンコーディングのフォールバック、OGP の属性順2パターン、`published_parsed` と `updated_parsed` の優先順、JST 変換、RDF フィードの解釈)と、一度解いた実行環境の問題(`pythonw.exe` のウィンドウレス起動。`node.exe` はコンソールアプリなので毎時ウィンドウが点滅する)を買い直すこと。polyglot の対価(venv・requirements・pytest が入る)は受け入れる。2026-08-14。
- 移設元 `mf/news_scraping` の git 履歴は存在しない(archive ではなく削除)。scraper のコードがそう書かれている理由は**コード内のコメントにしか残っていない**ので、コメントを消すと復元できない。

## finance ページは既存の資産計画の移設(2026-10-23 本人決定)

- 家計の見通しを Excel ブック(others/finance/finance_plan.xlsx)から `/finance` へ移した。月末の残高2個の記録と、計画(イベント表)を書き換えたときの資金配分の判断に使う面で、新しい日次入力習慣は要求しない。design.md 制約10の「毎日使うか」は、使う場面が「月末の記録」「お金を使う前に見通しを見る」と具体的に特定できているので足してよい、の適用。価値は閲覧回数ではなく、月次の記録と資金配分の判断がここで完結することで確かめる。
