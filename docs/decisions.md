# 設計判断の記録 — 面ごとに選んだことと理由

`docs/design.md` は「守る制約」と「未決」だけを持つ。ここは**個別の面・実装で選んだことと、その理由**を置く。廃止したものは現状(何を持たないか)だけを書く。Supabase の権限・migration・観測は `docs/database.md`。

## 面を足す・減らすときの判定(design.md 制約10の運用)

- 「使われ続けた」の観察判定が効くのは**新しい習慣を仮定する面**だけ。既存の習慣の置き場を移すだけの面には適用しない(`/news` は移設前から毎日読んでいたものの移設なので、判定対象になる不確実性が無い。2026-08-14)。
- 毎日でなくても、使う場面が具体的に特定できているなら足してよい(`/reports`:「電車内で確実に使う」2026-08-09)。読み取り専用の導出物は、使われなくなってもテーブルとページを消すだけで損失が出ない。過去に消えた面はすべて入力を伴う面だった。
- 反映が定時ジョブ(旧 taskbox の drain 枠など)でしか起きない非同期の面に人間の判断を通す経路を作るなら、**その往復が「セッションを開いて直接聞く」より速いことが成立条件**。成立しないなら読む専用にする(2026-08-11)。
- カードや行に分類軸(目標・タグ)を足さない。抱えられる数に見合わない分類は複雑性そのもの(2026-08-23)。
- 毎回少しずつ足す経路にある分量の規約は、散文で書いても守られない(300 字上限が制定後3週間で 14.6 倍になった)。機械判定できるなら投入の境界で弾くか切る(例: 廃止した `drain_runs` の要約上限は投入スクリプトで切り捨てていた)。
- 一覧の目的は網羅ではない。載せるかは「本人が待たれているか/再開の合図が近いか」で決め、「進行中か」では決めない。動いていない行が多いほど、動いた行が埋もれる。

## Schedules

- 日別メモ欄(`schedule_day_notes`)は予定欄と併設する。PC(`sm` 以上)は横並びで予定:メモ = **3:2**(本人指定。50:50 案は採らず)、スマホは縦積み(幅 375px で横2分割は両方とも実用に耐えない)。競合制御は inboxes と同じ last-write-wins で、予定側の楽観ロック経路(`replace_schedules_for_day` + `schedule_day_revisions`)には触れない。`DayEntry` 型には入れず `useDayNotes` が `Map<dayKey, string>` で独立管理する(`text-format.ts` / `sync.ts` とその検査への波及をゼロにするため)。2026-08-05。
- テキストエリアの最低高は 40px(1行 24px + `py-2`)。数値の根拠は `src/components/schedules/DaySection.tsx` のコメント。
- 既定予定(`default_schedules`)は、画面が日を読み込む直前に `apply_default_schedules` で**実データとして書き込む**(本人の要望「UIから見たすべての日に自動で入っていてほしい」、2026-09-28)。表示時に重ねるだけの仮想方式は採らない: その日だけ消す・ずらすたびに例外の記録が要り、日を丸ごと置換する保存経路と噛み合わない。書き込み済みの (既定予定, 日) は `default_schedule_applications` に残すので、その日の既定予定を消しても復活しない。帰結として、既定予定の時刻を変えたり削除したりしても、**書き込み済みの日(読み込んだ範囲 = 初回は今日から14日先まで。端に着くと1か月ずつ広がる)には反映されない**。`effective_from` より前の日には入れない(過去方向の無限スクロールの停止条件と過去の記録を守るため)。いま在る予定と時間が重なる既定予定は書かず、適用済みの印だけ付ける(2026-11-14。重なる行がある日は板が Invalid にするため)。追加・削除は monocore スキルの `defaults` コマンドから行い、画面には管理UIを持たない。

### 復帰同期のタイムアウト(2026-11-07、AI の判断。本人の指示は「スマホでスケジュールに戻ると Inbox がずっと開けない。原因を調べ、改善して」)

- **症状と原因**: Inbox ボタンは `disabled={isEditLocked}`(Tasks にはその条件が無い)。`isEditLocked` は復帰同期中の `isResumeSyncing` を含み、復帰同期の通信が決着しないとロックが降りない。しかも `isResumeSyncingRef` が立っている間は次の復帰を無視するので、再読み込みするまで戻らない。通信に上限が無かった(`createClient` は既定、`AbortSignal` も無し)。**どの通信が止まるかは実機で未確認**(スマホの凍結後に死んだ接続へ送る、が有力な推定)。
- **直したこと**:
  - 全通信に 15 秒の上限(`src/lib/supabase/fetch-with-timeout.ts`、`client.ts` の `global.fetch`。supabase-js は auth にも同じ fetch を渡すので `/token` の更新にも効く)。応答が返ってもタイマーは止めない(ボディ受信中の停止を拾うため)。postgrest-js は GET を最大3回やり直すので、上限を超えた GET は新しい接続でやり直される(死んだ接続からの復帰を兼ねる)。最悪 15×4+7=67 秒かかるので、復帰同期の上限をそれより長くした。書き込みはやり直さず、失敗として既存の打ち切りの経路に乗る。
  - 復帰同期全体に上限(目印の確認 75 秒、読み直し 75 秒。`runResumeSyncOnce`)。決着しなくてもロックと実行中フラグは必ず戻る。上限を超えた読み直しは `isAbandoned` で見限り(読み直しの後続・メモの反映・予定の反映を止める。手動の再読み込みの世代 `reloadEpoch` には触れない)、遅れて届いた古い結果で、その間に保存した予定やメモを戻さない。次の復帰は `forceReload` で目印によらず全読み直しする(`syncError` は編集で消えるので別に持つ)。
  - **編集ロックは読み直しの間だけ**。読むだけの目印確認では掛けない(これまでは2秒離れただけでも毎回、入力が黙って捨てられ Inbox が無効になっていた)。掛ける前後に保存の完了を待ち、編集中・未保存のメモがあれば置き換えずに見送る。
  - 復帰同期の見送り条件から **Inbox の未保存を外した**(予定の読み直しは Inbox に触れない。最初のリファクタ 9bd8b97 以来で、残された理由は無い)。見送った同期は、フォーカスが外れて未保存のメモが無くなったときにやり直す。戻ったときに未保存のメモが残っていれば保存し直す。`online` でも同じ復帰同期を試す。初回の読み込み中は走らせない。
- **採らなかった案**: (1) Inbox ボタンを編集ロックから外す: ロックが読み直しの間だけで上限付きになったので、挙動を変える理由が弱い。(2) 離れていた時間の閾値で同期を省く: ロックを狭めたので不要で、本人の好みに触れる。(3) 復帰時のリクエスト数の削減(目印3本+Inbox1本+認証更新が同時に出る): 別件。
- **astra の意見(採用)**: 期限切れ後の遅延完了を無効化する世代番号、強制再同期フラグを `syncError` から独立させる、ロック後の保存待ち、見送りの再評価を状態変化に連動させる、`withTimeout` 単体でなく「期限切れ後に再び同期できる」ことのテスト。
- **未検証**: 実機で止まっていた通信の特定、応答消失後の保存(サーバでは成功済みで、再試行が競合して dirty を落とす経路)。後者は既存の `decideAfterSave` の打ち切りに乗る。再発したら、止まった通信を `console` に出して特定する。

- 項目は本人指定: 時刻・天気・気温・降水確率・降水量(降雪量)・湿度・風向風速を1時間ごと、加えて日の出・日の入り。
- 形は AI が横スクロール表・予定と統合・グラフ・要約の4案、続いて縦のグラフ2案を出し、本人が次のように絞った:
  > デスクトップでもモバイルでも横スクロールはしたくない。縦に伸びるのは許容する。
  > グラフはかえってみずらいかも。本家にならってこんな感じで作ってみて。
  - 結果は tenki.jp のモバイル版と同じ、日ごとに区切った縦の表。グラフは使わない。
- 置き場所は本人指定: 新規ページで、サイドバーの Schedule と Reports の間。
- 同日、デスクトップの左右の余白を本人が嫌い(「desktopで左右に余白があるのが気に入らない」)、AI が挙げた案のうち週間予報を足す方を本人が選んだ(「そういえば週間予報つかっているわ」)。tenki.jp の週間予報と同じ1日1行の表で、デスクトップは右列。
- 天気の言い方の規則は AI がモックで示し、本人は気温の表示だけ直させてそのまま採った: 6〜11時と12〜17時で多い区分(晴・曇・雨・雪)が違えば「AのちB」、同じで6〜17時に別の区分が2時間以上あれば「A時々B」。霧雨も雨に数えるので、降水確率が低いのに「雨」になる日がある。
  > 気温が4桁の数字に見えるので、それだけ直して実装して
  - 最高・最低は「20° / 16°」と ° と / で区切る。
- tenki.jp にある信頼度(A〜E)は Open-Meteo に無いので出さない。
- 予報はブラウザ(localStorage)に置く(本人の求め 2026-11-13「頻繁に開くのでキャッシュしたい」。DB 保存は「必要ならDB保存も考える」とのことで、まず localStorage にした)。取り直しの間隔は本人指定で2時間。2時間以内なら取りに行かず、古ければ手元の分を先に出して裏で取り直す。手動更新は常に取りに行く。ログアウトで消す。`src/lib/weather/cache.ts`。DB に置くのは、端末をまたいで共有したくなったときに再検討する。

## /reports ミラー

- 方式は読み取り専用ミラー。読む場面はラップトップがスリープ中の電車・ベッドなので 24/7 可用性が必須で、Tailscale + ローカル HTTP はスリープで死に、GitHub private repo は reports 側の規約が禁止している。閲覧専用なので双方向同期の難所(schedules が日単位版管理で払ったコスト)が丸ごと要らない。2026-08-09。
- 全件同期(ホワイトリストで選別しない)。reports のコミットと upsert をセットで走らせ(`mf/ops/sync-reports.ps1`)、ミラーが腐らないようにする。
- 同期は「集合の一致」であって upsert ではない(ローカルに無い slug は delete。`scripts/upsert-reports.mjs`)。upsert だけだと削除・archive 移動・リネームがミラーに残り続け、「ローカルが正」が破れる。
- 導出物は単一形式でのみ持つ(md と HTML の二重保持をしない)。片方を捨てて失う機能は**列を足さず別の手段で代替**する(本文の全文検索はタイトルと見出しのみに絞り、本文内はブラウザのページ内検索に任せる)。容量は律速ではない(reports 約 1MB/月、無料枠 500MB、2KB 超の text は TOAST が圧縮)。この2原則は容量対策ではなく正しさのために採る。
- `_index.md`・`CLAUDE.md`・`archive/` は同期対象外。索引にだけ書いた注記(「この結論は死んでいる」等)はスマホから本文を開く読み手に届かない。そういう警告は本文の冒頭に書く。
- 開いたレポートの本文はブラウザ(localStorage)に置き、次に開くときは updated_at だけを問い合わせて、変わっていたときだけ本文を読む(本人の指示 2026-10-23。本文は中央値約 40KB、最大約 600KB)。通信が無くても一度開いたものは読める。ログアウトで消す。`src/lib/reports/cache.ts`。

## /news と scraper

- 保持は 8 日で物理削除。DB に蓄積して表示側だけ直近 N 日に絞る案は採らなかった(2026-08-14)。
- scraper は Python のまま置き、node へ書き直さない。統合で得たいもの(フォルダをなくす・スキーマとライターを同じコミットに乗せる)は言語に依存しない。書き直しの対価は、既に直したバグ(エンコーディングのフォールバック、OGP の属性順2パターン、`published_parsed` と `updated_parsed` の優先順、JST 変換、RDF フィードの解釈)と、一度解いた実行環境の問題(`pythonw.exe` のウィンドウレス起動。`node.exe` はコンソールアプリなので毎時ウィンドウが点滅する)を買い直すこと。polyglot の対価(venv・requirements・pytest が入る)は受け入れる。2026-08-14。
- 移設元 `mf/news_scraping` の git 履歴は存在しない(archive ではなく削除)。scraper のコードがそう書かれている理由は**コード内のコメントにしか残っていない**ので、コメントを消すと復元できない。
- サムネイルは scraper が 480×320 の WebP に縮めて Supabase Storage の公開バケット `news-thumbs` に置き、`articles.image_url` はその URL を指す(2026-11-15)。og:image 原寸(実測: 幅の中央値 1200px・1枚の中央値 229KB・最大 2.9MB)を 160×107 CSS px の枠に読んでいて、初回表示だけで約 11MB だった。縮小後は 1枚 約 13KB。外部のリサイズ中継(wsrv.nl 等)は依存と閲覧先の漏えいが増えるので、`next/image` は Vercel の画像最適化の無料枠を毎日入れ替わる記事で超えやすいので採らなかった。作れなかった記事は元の URL のまま保存して続行し、`python run_once.py --backfill` で作り直す。期限切れの記事の画像は、行を消す前に scraper が消す(順序の理由は `scraper/run_once.py`)。

## 認証ゲートの一部をプロキシからクライアントへ移した(2026-11-23。AI が本番を実測して提案し、本人が「進む」と採った)

- 動機は本人の次の2つの発言。
  > react/nextjsで作ったサイトが超遅いのだがこれってそんなもん？
  > mf/monocoreとか、コンポーネントもデータもすごく小さいのに遅い
- 2026-11-22 に本番(東京から、ログイン済み)を実測して、サーバー側の遅さの原因を2つに分けた。
  1. 関数のリージョンが iad1(米国東部)だった。DB はシンガポール(ap-southeast-1)なので、東京 → 米国東部 → シンガポールの経路になっていた。本人が Vercel の設定を hnd1(東京)に変えた。変更後、動的ルート(`/weather`、`/reports/*`)の応答は warm の中央値で約 350〜380ms → 約 145ms、冷えた最初の1回は 919ms → 397ms。
  2. プロキシを通るだけで、ページ取得のたびに約 110ms が乗る。プロキシを通らない静的ファイルは 16ms、通る静的ページは中央値 126ms、Cookie なしでも 110ms。認証でもリージョンでもなく、プロキシ関数の起動そのものの固定費。本番では読み込みごとにサイドバーの先読みが 18〜21 本走り、それぞれがこの固定費を払っていた。
- 殻のページ(`/`・`/schedules`・`/finance`・`/news`・`/reports`)は、HTML にデータを持たず、データはブラウザから Supabase へ直接取りに行く(RLS で守る)。サーバーで門番をしても守るものが無いので、matcher から外した。未ログインは `AuthGate`(`src/components/auth/AuthGate.tsx`)がブラウザ側で `/login` へ送る。
- 外さないもの: `/weather`(`connection()` の後で地点を HTML に入れるので、ログインを通る前に見えてはならない)、`/login`、`/auth/callback`、未知のパス、`/reports/<slug>`。`/reports/<slug>` は殻だが、開いたレポートの本文を localStorage から、`AuthGate` の確認より先に出す。外すと、セッションの無いブラウザ(Cookie だけ消した、など)に保存済みの本文が、`/login` への転送が終わるまでの数百 ms 見える。サーバーの門番なら HTML を返す前に転送する。sol のレビュー(2026-11-23)の指摘で戻した。レポートを開くたびの約 110ms は残る(`/reports/<slug>` は動的ルートで、もともとプロキシ + 関数を通っていたので、今回の変更の前と同じ)。matcher は「外す殻を列挙する」形にしたので、新しいルートを足して matcher を触り忘れても、既定でプロキシを通る(遅くなるだけで門番は外れない)。境目は `src/proxy.test.ts`(Next.js 自身の `unstable_doesMiddlewareMatch` で判定)。
- `AuthGate` の決め事: `getSession` は通常は Cookie を読むだけで、アクセストークンが期限切れ間近のときだけ更新の通信が出る(どのページもすぐ後に同じ更新を要るので、増える通信は無い)。`error` のとき(電波が弱いだけ)は `/login` へ送らない。更新トークンの失効と別タブでのログアウトは `SIGNED_OUT` で `/login` へ送る。
- 採らなかった案: (1) リージョンだけ変えて全ページをプロキシに通したまま: 約 110ms が残る。(2) Next.js をやめて別のフレームワークへ: JS の差は 50〜100KB 程度で、遅さの主因(プロキシの固定費、`/schedules` の初回ロードの直列3往復、textarea の高さ計算)はフレームワークに依らない。
- 開発サーバーでは、殻のページを未ログインで開くと、`/login` で自動ログインしてから `/` に着く。元のページには戻らないので開き直す。自動ログインが失敗したとき(ローカル Supabase が止まっている、`DEV_AUTH_*` が誤っている)は `/` へ送らず `/login` を出して止める。以前は失敗しても `/` へ送っていたので、殻のページの `AuthGate` と `/` ⇄ `/login` を往復し続けた(sol の指摘)。
- 別件だった `/schedules` の textarea 138個の高さ計算(1周 約 138ms。読み込み中に2〜3周)と、初回ロードの Supabase 直列3往復は、下の「/schedules の初回ロードを縮めた」で直した。

## /schedules の初回ロードを縮めた(2026-11-23。AI が本番を実測して直し、本人が「進む」と採った)

- 修正前の実測(本番、東京の 14 コア PC、Finance → Schedules の画面内移動を3回): 「同期中」の幕が消えるまで 686〜1059ms(中央値 857ms)、マウント時の long task 167〜185ms(最初の API 呼び出しはクリックの 172〜190ms 後)。本番のデータは textarea 138 個のうち 80 個が内容あり(既定予定が実データとして全日に入っているため)。
- 修正後の実測(本番、同じ手順・同じ PC、コミット 5fd2bbe): 幕が消えるまで 525〜579ms(中央値 546ms。修正前の中央値 857ms から約 310ms 短縮)。マウント時の long task は消え(修正前 167〜185ms)、データ到着直後の long task 85〜96ms は変わらない。最初の API 呼び出しはクリックの 22〜33ms 後(修正前 172〜190ms)、API の完了は 417〜484ms(修正前 596〜955ms)、API の呼び出しは 10 本から 9 本(空のページの往復が消えた)。表示内容と textarea の高さの指紋(138 欄)は修正前と同じで、再読み込み後も同じ。初回の範囲が約 69 日だったときの値(下の 14 日の項で範囲を変えた後の基準値は、そちらを見る)。
- 直したこと:
  1. **空の欄の高さを測らない**(`AutoHeightTextarea.tsx` の `fitHeight`)。読み込み直後は 138 欄すべてが空で、欄ごとに `scrollHeight` を読むたびに強制レイアウトが走り、1周 約 138ms かかっていた。空の欄は既定の高さ(rows=1 + 最低高)のままでよく、前に測った高さが残っていれば外すだけ。空の欄 58 個で、明示の高さを外しても `offsetHeight` が変わらないことを本番で確かめた。
  2. **`getDefaultAppliedDays` が空のページを読まない**(`queries/schedules.ts`)。空のページが返るまで読んでいたので、読み込みごとに空を返すだけの往復が1つ残り、ほかの読み込みが終わった後に完了を約 100ms 遅らせていた。終わりの判断は、`count: 'exact'` で取った総数に読んだ行数が届いたこと(総数が取れないときは従来どおり空のページまで読む)。「1ページ(`PAGE_ROWS`)に満たなければ最後」にしなかったのは、本番の PostgREST の `max_rows` が `supabase/config.toml` の 1000 と一致する保証がなく、小さいと短い応答を末尾と見誤って「既定予定の記録の無い日」を黙って取りこぼすため(sol の指摘。0・1000・1001 行・`max_rows` が小さい場合・途中のエラーを `queries/schedules.test.ts` で確かめている)。同じファイルの版の目印とメモの目印は、まだ「1ページに満たなければ最後」で、`max_rows ≧ 1000` に依存している(別件)。
  3. **初回の読み込みで、既定予定の書き込みと目印の取得を同時に出す**(`useSchedules.ts` の初回 effect だけ。`reloadSchedules` と無限スクロールの継ぎ足しは従来の順のまま)。直列は「書き込み → 目印 → 読む」の3往復だった。目印は読む前に取ればよく、書き込みの後である必要は無い: 書き込みが予定や版を足した日は、目印が読んだ内容より古い向きに食い違うが、次の復帰で余分に1回読み直すだけで、変更の見落としにはならない。目印が読んだ内容より新しくなることは無い(読むのは両方が終わってから)。書き込みを待ってから予定・版を読むことは変わらない。なお、初回の書き込みより先に目印の取得が走って、書き込みが目印に映らなかった場合は、そのあと範囲を広げる(無限スクロール)際に `readChunkStamp` が取り直した旧範囲の予定の目印が手元の目印と食い違い、目印の合成を見送る(古い向きに食い違った目印を新しい範囲へ引き継がない)。そのときは広げる処理も表示も成功し、次の復帰で全読み込みになるだけ。書き込みが目印に映っていれば合成される。毎回ではない。
