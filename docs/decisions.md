# 設計判断の記録 — 面ごとに選んだことと理由

`docs/design.md` は「守る制約」と「未決」だけを持つ。ここは**個別の面・実装で選んだことと、その理由**を置く。廃止したものは現状(何を持たないか)だけを書く。Supabase の権限・migration・観測は `docs/database.md`。

## 面を足す・減らすときの判定(design.md 制約10の運用)

- 「使われ続けた」の観察判定が効くのは**新しい習慣を仮定する面**だけ。既存の習慣の置き場を移すだけの面には適用しない(`/news` は移設前から毎日読んでいたものの移設なので、判定対象になる不確実性が無い。2026-08-14)。
- 毎日でなくても、使う場面が具体的に特定できているなら足してよい(`/reports`:「電車内で確実に使う」2026-08-09)。読み取り専用の導出物は、使われなくなってもテーブルとページを消すだけで損失が出ない。過去に消えた面はすべて入力を伴う面だった。
- 反映が drain 枠でしか起きない非同期の面に人間の判断を通す経路を作るなら、**その往復が「セッションを開いて直接聞く」より速いことが成立条件**。成立しないなら読む専用にする(2026-08-11)。
- カードや行に分類軸(目標・タグ)を足さない。抱えられる数に見合わない分類は複雑性そのもの(2026-08-23)。
- 毎回少しずつ足す経路にある分量の規約は、散文で書いても守られない(300 字上限が制定後3週間で 14.6 倍になった)。機械判定できるなら投入の境界で弾くか切る(`drain_runs` の要約上限は `scripts/drain-run-payload.mjs` で切り捨て)。
- 一覧の目的は網羅ではない。載せるかは「本人が待たれているか/再開の合図が近いか」で決め、「進行中か」では決めない。動いていない行が多いほど、動いた行が埋もれる。

## プロジェクト板は持たない(2026-09-11 廃止)

- `/projects`・`project_cards` テーブル・taskbox 側のカード生成を廃止し、テーブルも DROP 済み(migration `20260911202118`)。理由(本人): 利用頻度が落ち、半ば義務化していた。2026-07-17 の旧 projects 削除(「ほとんど見ていなかった」)に続き2度目。
- プロジェクトの背景・状況・進行中一覧は monocore に持たない。人間がやる期日ありのタスクは schedules に置く。

## Schedules

- 日別メモ欄(`schedule_day_notes`)は予定欄と併設する。PC(`sm` 以上)は横並びで予定:メモ = **3:2**(本人指定。50:50 案は採らず)、スマホは縦積み(幅 375px で横2分割は両方とも実用に耐えない)。競合制御は inboxes と同じ last-write-wins で、予定側の楽観ロック経路(`replace_schedules_for_day` + `schedule_day_revisions`)には触れない。`DayEntry` 型には入れず `useDayNotes` が `Map<dayKey, string>` で独立管理する(`text-format.ts` / `sync.ts` とその検査への波及をゼロにするため)。2026-08-05。
- テキストエリアの最低高は 40px(1行 24px + `py-2`)。数値の根拠は `src/components/schedules/DaySection.tsx` のコメント。
- 既定予定(`default_schedules`)は、画面が日を読み込む直前に `apply_default_schedules` で**実データとして書き込む**(本人の要望「UIから見たすべての日に自動で入っていてほしい」、2026-09-28)。表示時に重ねるだけの仮想方式は採らない: その日だけ消す・ずらすたびに例外の記録が要り、日を丸ごと置換する保存経路と噛み合わない。書き込み済みの (既定予定, 日) は `default_schedule_applications` に残すので、その日の既定予定を消しても復活しない。帰結として、既定予定の時刻を変えたり削除したりしても、**書き込み済みの日(読み込んだ範囲 = 概ね今日から2ヶ月先まで)には反映されない**。`effective_from` より前の日には入れない(過去方向の無限スクロールの停止条件と過去の記録を守るため)。追加・削除は monocore スキルの `defaults` コマンドから行い、画面には管理UIを持たない。
- 空の日を折りたたむ抜本策は採らない。スクロール長の真因は「空の日が空のまま場所を占めること」だが、折りたたみは「どの日にもすぐ書ける」性質を壊す。最低高の縮小はその緩和策。

## /reports ミラー

- 方式は読み取り専用ミラー。読む場面はラップトップがスリープ中の電車・ベッドなので 24/7 可用性が必須で、Tailscale + ローカル HTTP はスリープで死に、GitHub private repo は reports 側の規約が禁止している。閲覧専用なので双方向同期の難所(schedules が日単位版管理で払ったコスト)が丸ごと要らない。2026-08-09。
- 全件同期(ホワイトリストで選別しない)。reports のコミットと upsert をセットで走らせ(taskbox 側)、ミラーが腐らないようにする。
- 同期は「集合の一致」であって upsert ではない(ローカルに無い slug は delete。`scripts/upsert-reports.mjs`)。upsert だけだと削除・archive 移動・リネームがミラーに残り続け、「ローカルが正」が破れる。
- 導出物は単一形式でのみ持つ(md と HTML の二重保持をしない)。片方を捨てて失う機能は**列を足さず別の手段で代替**する(本文の全文検索はタイトルと見出しのみに絞り、本文内はブラウザのページ内検索に任せる)。容量は律速ではない(reports 約 1MB/月、無料枠 500MB、2KB 超の text は TOAST が圧縮)。この2原則は容量対策ではなく正しさのために採る。
- `_index.md`・`CLAUDE.md`・`archive/` は同期対象外。索引にだけ書いた注記(「この結論は死んでいる」等)はスマホから本文を開く読み手に届かない。そういう警告は本文の冒頭に書く。

## /news と scraper

- 保持は 8 日で物理削除。DB に蓄積して表示側だけ直近 N 日に絞る案は採らなかった(2026-08-14)。
- scraper は Python のまま置き、node へ書き直さない。統合で得たいもの(フォルダをなくす・スキーマとライターを同じコミットに乗せる)は言語に依存しない。書き直しの対価は、既に直したバグ(エンコーディングのフォールバック、OGP の属性順2パターン、`published_parsed` と `updated_parsed` の優先順、JST 変換、RDF フィードの解釈)と、一度解いた実行環境の問題(`pythonw.exe` のウィンドウレス起動。`node.exe` はコンソールアプリなので毎時ウィンドウが点滅する)を買い直すこと。polyglot の対価(venv・requirements・pytest が入る)は受け入れる。2026-08-14。
- 移設元 `mf/news_scraping` の git 履歴は存在しない(archive ではなく削除)。scraper のコードがそう書かれている理由は**コード内のコメントにしか残っていない**ので、コメントを消すと復元できない。

## /drain 報告板

- 組の材料は機械値だけ(`drain.ps1` の観測値と、セッションの最終報告の全文)。セッションに構造化ブロックを出させない: 無人経路に自己申告を増やさない、薄い→厚いは後から足せるが逆は面倒。2026-08-12。
- 載せるのは4点(何をやったか/成否/失敗の理由/想定外に起きたこと)。①②は1タスク1文まで畳み、③④は畳まない。縮めるのは平常運転の記述だけで、本人が動く必要のあるものは縮めない(2026-08-15、粒度は 2026-08-30 改訂)。
- 2026-09-12 以降、traces 由来のタスク別詳細(summary / failures / notes / 委譲)は表示しない。板に出るのは最終報告の全文だけ(暫定。本人「なんなら報告全文すらもなくすかも」)。taskbox は `tasks` に空配列を送る。
- 保持 48 件、連続スキップは1枚に畳む、crashed は畳まない(理由はそれぞれのコードのコメント)。
- **本人が手を動かさないと片づかないこと(依頼)は、run のカードとは別枠で先頭に出し、本人が「済」にするまで残す**(`drain_asks`、2026-10-05 本人判断「monocoreのdrain板に出す」)。それまでの届け先 `taskbox/handover.md` の「本人判断待ち」は本人が開かない面で、答えが出たのは本人がその話題の対話セッションにいたときだけ、ほかは7日後に黙って退避されていた(平文認証情報の件は08-31から未対応)。run のカードに載せると48件の保持で約2日後に消えるので、同じ失敗になる。
  - 依頼の有無は機械で観測できないので、これは 2026-08-12 の「セッションに構造化ブロックを出させない」の例外になる(trace の `asks[]` がセッションの自己申告)。載せてよいのは本人の手が要るものだけで、成果物の設計上の分岐はそのリポジトリの docs、実行済みで戻せる措置への事後確認は出さない(規約は taskbox/README.md)。
  - 「済」は判断を drain へ返す経路ではなく、表示から外すだけ。上の「人間の判断を通す経路」の成立条件には当たらない。

## inbox は人間が毎日読む参照リストと手順の置き場(2026-08-13 本人判断)

- 読みたい本・筋トレメニュー・発声トレーニング・会話術などの参照リストに加え、毎日実行する手順(スローブリージング、口腔咽頭筋機能療法)も inbox に置く。本人の理由: 「いつでもどこでも見返して実行できるように」(デスク前に限らずスマホから読める面が要る)。design.md §2 で持ち越していた「参照リストの置き場」はこれで決着し、名前付きテキスト面を別に持つ案は採っていない。
- 経緯: knowledge 削除後、中身は消えずに inbox ブロブへ移った。knowledge が空になったのは使われなかったからではなく、レコード型 CRUD の入力コストが単一テキストエリアへの追記に負けたため(推定)。
- **注意**: 呼吸法と口腔咽頭筋機能療法の手順本文は 2026-08-29 の空文字上書き(database.md)でどのバックアップにも残らず失われ、2026-08-30 に Claude が engine に残っていたパラメータと一般的な myofunctional therapy のプロトコルから再構成したもの。回数・秒数などの細部は原文と食い違う可能性があり、本人が違和感を覚えたら書き換える。
