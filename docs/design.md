# monocore 設計 — 守る制約と、未決の問い

このファイルが持つのは2つだけ:

1. **実装が守る制約**(決定済み・理由つき)
2. **まだ決まっていないこと**(決まっているふりをしない)

**実装済みの構造・ルールはREADMEにある**(ルート・テーブル・投入経路・禁止事項)。ここには書かない。

**フェーズ計画(旧 `monocore-v2-design-draft.md` の Phase 1〜4)は2026-08-06に廃止した。** 理由は§3。

前提: monocoreは context-engine(記憶系)・taskbox(実行系)に次ぐ**AI活用基盤の第三の柱**であり、**人間が触る唯一の窓口**(2026-07-14決定、2026-08-06に凍結解除して再確認)。ユーザーはengine/taskboxのmdやターミナルを開かない。

## 1. 守る制約(決定済み)

### 構造

1. **3システムは互いを知らない。結合はすべてローカルPC上のブリッジ(=Claudeセッション)が担う。** monocoreはengine/taskboxのファイルを読まず、engine/taskboxはmonocoreを知らない。統合面は**monocoreのSupabaseスキーマただ1つ**(テーブル+RLS+service roleの契約)。engine/taskboxの形式が変わってもブリッジだけ直せばよく、monocoreを別物に置き換えてもengine/taskboxは無傷。(2026-07-14)

   ```
   taskbox ──→ engine          (既存・不変)
   bridge  ──→ engine / taskbox / monocore(Supabase)
   monocore ──→ (どこも参照しない)
   engine  ──→ (どこも参照しない)
   ```

2. **正の所在**: 人間が書いたデータ=monocore / 実行状態=taskbox / 永続文脈=engine。**monocore内の導出物(`drain_runs`等)は使い捨て**で、消えても再生成できる。したがって**導出物に手入力欄を作らない**。書き込みが要る面は`schedules`・`schedule_day_notes`・`inboxes`に限る。(2026-07-14 / 2026-08-03 / 2026-08-09 / 2026-08-11)

3. **ブリッジは薄く保つ。** エージェント機能は既存のClaude(スキル・taskboxプロトコル)をそのまま使い、ブリッジは配送と写像だけを行う。自前エージェント基盤を作らない(monarcsの失敗)。

3-a. **正の所在には第3の分類がある(2026-08-14追加)。** 制約2は「人間が書いたデータ」と「使い捨ての導出物」の2つしか想定していなかったが、`articles`(RSSで集めた記事)は**どちらでもない** — 人間は書かないが、RSSは過去記事を配らないので消えても再生成できない。したがって**正はmonocoreのDB自身**にある。保持8日を選んだので失われうる最大値は「8日以内に読み逃した記事」であり、バックアップは持たない。**この分類がもう1つ増えるなら、そのとき改めて考える**(1つのために一般則を作らない)。

3-b. **収集ジョブをmonocoreに置いてよいのは、その出力をmonocoreの面が表示する場合に限る(2026-08-14制定)。** `mf/news_scraping`を吸収した結果、monocoreは「人間向けの窓口＋導出物の受け皿」に加えて**外界から取り込むワーカー**(`scraper/`)を持った。妥当だが、次に別の収集対象が来たときに雑多なジョブ置き場になる入口でもある。面を持たない収集は実行系(taskbox)の管轄。

### インフラ・結線

4. **Supabase(クラウド)を維持する。** ローカルSQLite移行も自宅の常時稼働ノードも却下済み。動機は**運用のシンプルさ**(ハードウェアと接続経路を増やさない)であり、ローカル化はTunnel等で接続を複雑にし、常時稼働ノードはハードウェアを増やすため、いずれも動機に反する。ラップトップがスリープ中でもスマホから予定を見る要件があるので24/7可用性は代替が効かない。(2026-07-14)

5. **PCは受信ポートを開けない。** ブリッジからのアウトバウンド接続のみ。Cloudflare Tunnelは不要。service key・ブリッジ資格情報はローカルPCの外に出さない。

6. **結線はポーリング。常駐WebSocket(Realtime)は使わない。** taskboxのdrainと同型にすることで、再接続処理が不要になり、drainで既に得ている運用知見をそのまま流用できる。(2026-07-20。2026-07-14の「メッセージバスはRealtimeで確定」を撤回)

7. **非同期が第一級。** ブリッジ停止中(ラップトップスリープ)もデータのCRUDと投稿は常時成立し、ブリッジ起床時に未処理分を古い順にキャッチアップする。UIは即答を約束せず、状態を明示する。ブリッジが死んでも失われるものはない(DBに残り次回起床で消化)。(2026-07-14、体感の許容も2026-07-16に確認済み)

### 権限・安全

8. **破壊的操作はラチェット式の2ターン確認。** 操作のリスクは種別だけでは決まらない(同じ削除でもスクラッチとengineでは別物)ので文脈を見る層は要るが、その層を信用しすぎない:
   - **自動実行可の範囲はLLMの外の決定論的ルールで定義する。** LLMは許可リスト内の操作を2ターンへ**引き上げられるが、確認対象を直接実行へ引き下げられない**。判定するのは実行したがっている本人と同じコンテキストで、直前に読んだノート・handover・外部テキストに汚染されうるため。
   - **2ターン目は再計画ではなく事前固定した操作の実行。** 確認レコードに実際のSQL/コマンド/パラメータを保存し、承認時はそれを実行するだけにする。ポーリング型でセッションが毎回別プロセスになる以上、実装上も必須。(2026-07-20)

9. **DBに認証情報(ID/パスワード等)を置かない。** service keyはRLSを迂回するため、inboxを読むAIセッションは自動的に全行を読む。2026-07-21に平文の認証情報がinbox本文から発見され、2026-08-05にパスワードマネージャへ移設・残存0を検証済み。

### 面を増やすときの判定

10. **合格基準は「動いた」ではなく「使われ続けた」。** 疎通の確認を価値の確認と書かない。一度作って使われないまま削除した面が既に5つある(旧projects / tasks / knowledge / schedulesの要注意タスクパネル / プロジェクト板 `project_cards`(2026-08-03〜09-11))。**足す前に「これは本当に毎日使うか」を問う。**「第三の柱として育てる」は作り込みの許可であって、作り込みの要求ではない。(2026-07-20の教訓、2026-08-06に再確認)。この基準の運用(適用しない場合・毎日でなくても足す場合)は `docs/decisions.md`。

11. **inboxパネルは当面残す。** ブリッジ(ラップトップ)が寝ている間に成立する唯一のモバイル書き込み経路であるため。**廃止の条件は「チャットが実装された」ではなく「inboxへの投稿が自然にゼロになった」。**(2026-07-20)

## 2. まだ決まっていないこと

以下は**決まっていない**。ロードマップとして書かない — 過去にそれをやって腐った(§3)。

- **次に何を作るか、いつ着手するか。** 決まっていない。実際の着手は毎日の運用で痛みが出た箇所から発生している(§3)ので、それでよいと考えるならこの欄は空のままが正しい。
- **チャット窓口をやるのか。** 2026-07-20に「最優先はClaudeの自律性向上であって遠隔アクセシビリティではない、機械が先でリモコンが後」と判断して以来、着手していない。この優先順位判断は撤回されていない。**着手のトリガーを決めていない。**
- **チャット窓口の合格ラインをどこに置くか。** 2026-07-20に「予定を編集できるチャットでは不足で、engineをマウントしスキル・taskboxを持った本物のClaudeセッションがスマホから使えること」まで引き上げたが、その根拠だった「会話で予定を入れる機能はいらない」は**2026-08-06に撤回された**(Claudeアプリからの予定挿入は現在使用中)。**引き上げた合格ラインは導出としては無効**であり、結論としてなお正しいかは改めて判断が要る。
- **人間が常時読む参照リスト(読みたい本70冊超・トレーニングメニュー等)の置き場。** 2026-07-21から持ち越し。knowledge削除後、中身は消滅せずinboxブロブへ移動した。knowledgeが空になった原因は「使われなかった」ではなく**レコード型CRUDの入力コストが単一テキストエリアへの追記に負けた**と推定される。選択肢は(a)純参照リストだけ基盤の外の既製ツールへ出し「窓口はmonocoreに一本化」を限定撤回する (b)monocoreに名前付きテキスト面をN枚持たせる(**レコード型CRUDにはしない**)。**inboxの整理を設計するなら参照リストの行き先を先に決めること** — 決めずに仕分けを始めると参照リストだけが必ず残る。
- **通知(Web Push)・PWA化をやるか。** 未判断。現状monocoreに通知は一切ない。
- **taskboxのタスク粒度の写像(`board_mirror`)が要るか。** 未判断。要るとしても要約で足りるか、タスクmd全文まで見せるかは実装時。
- **AI編集マークの表示と`updated_by`の粒度**(日単位で`agent`に塗られる問題)。2026-07-21に**追跡打ち切り**。再開するなら改めて判断が要る(凍結解除で自動復活はしない)。
- **音声入力の非画面トリガー。** 画面操作での音声トグルは本人が嫌悪。Webでのウェイクワードは制約が多く、イヤホンのメディアボタン流用・PWAショートカット等の現実解は未調査。
- **失われた決定**: 2026-07-20にPhase 3の「3a/3b/3c分割」を確定したという記録がengine側にあるが、**分割の内容はどこにも残っていない**。着手するなら議論はやり直しになる。

## 3. なぜフェーズ計画を捨てたか(2026-08-06)

旧ドラフトは Phase 1(AI編集権) → 2(毎日の面への集約) → 3(チャット窓口) → 4(エージェントセンター) というロードマップを骨格にしていた。実績は以下:

| 実装されたもの                   | 由来                        | 結果                  |
| ------------------------- | ------------------------- | ------------------- |
| Phase 1 AI編集権スキル(7/17)    | フェーズ表                     | 稼働中(ただし判定が定まるまで3週間) |
| Phase 2 要注意タスクパネル(7/17)   | フェーズ表                     | **同日撤回・削除**         |
| プロジェクト板 `/projects`(8/3〜) | 朝の文脈回復コストという実地の痛み(表では4番目) | 2026-09-11に廃止(利用頻度が落ち、半ば義務化していた) |
| schedulesの日別メモ欄(8/5)      | 実地の痛み(表になし)               | 稼働中                 |
| メモ欄とtaskboxの回収連携(8/5)     | 実地の痛み(表になし)               | 稼働中                 |

捨てる理由は2つ。

1. **表は着手順を予測できなかった。** 稼働している5件のうち3件は表に存在しない項目で、表にあるPhase 3を飛ばしてPhase 4相当が先に入った。実際の駆動は「毎日の運用で痛みが出た箇所」であり、表は予測にも拘束にもなっていない。
2. **表は腐っても誰も気づかなかった。** 2026-07-18を最後に更新が止まり、その後に確定した決定6件(ポーリング化・権限モデル・inbox存続・Phase 1の価値評価・プロジェクト板・凍結と解除)を1件も反映しないまま2026-08-06まで放置された。**実装が参照しない計画表は、腐っていることが観測されない。**

なお2026-08-06までは「フェーズ表から作ったものは全部死んだ」がこの節の主論拠だったが、**Phase 1の不使用判定が同日撤回されたため取り下げた**。結論(表を捨てる)は上の2点で維持される。

したがってこのファイルは計画を持たない。持つのは、何を作るにせよ守る**制約**と、決まっていないという**事実**だけにする。

## 4. 長期の願望(未検証・拘束力なし)

2026-07-14に書いた完成イメージ。**決定ではなく願望**であり、検証されていない。作るものを決める材料としては使ってよいが、根拠としては使わない。なお2026-07-20〜08-06の間はこのうち「会話で予定を入れる」が不使用として否定されていたが、**撤回済み**(現在は使用中)。

> ユーザーはmdファイル群・ターミナル・Supabase管理画面を一切開かない(開発作業を除く)。生活のすべての接点はmonocore。朝はスケジュール面と判断待ちカード、電車ではラップトップがスリープでも閲覧・編集・カードへの回答が成立し、思いつきは音声で投げれば「受付済み」と表示される。研究室でラップトップを開くとブリッジが起床して溜まった分を消化し、予定が更新され、つぶやきはengineに記録され、回答したカードはtaskboxへ書き戻ってqueueに昇格する。夜はプッシュ通知で結果を受け取る。リストはAIが会話から更新し続けるため常に新鮮で、「読みに行く価値」が維持される。書く手間は「話す」まで下がる。
