# 空き時間と睡眠の数え方 — 形式的な定義と方式の判断

`src/lib/schedules/free-time.ts`(帯・自由時間・`/plan` の判定)と `src/lib/plan/` の数え方を、場合分けを足して直すやり方から、1つの定義とそれを確かめるテストで守るやり方へ移すための調査と判断(2026-10-18)。数え方の仕様そのもの(睡眠・非自由・自由の3区分、消灯の終わりから次の起床までが睡眠、など)は本人が決めたもので、正は `docs/decisions.md` の「空き時間の表示と /plan」節にある。このファイルが持つのは、その仕様の形式的な定義・方式の比較・守る性質・本人判断カードとその決定・実装の記録。本人は 2026-10-18 に6枚のカードをすべて推奨どおりと決め、同日に実装した(§7・§9)。

## 0. 結論

- **今の実装は、5件の fix の後で、下の定義(§2)と同じ振る舞いをしている。** 今の実装・区間の集合演算で書いた試作・「分ごとに最後の印を見る」素朴な参照実装の3つが、ランダムに作った約10,500件の予定ですべて全分一致した(§6)。
- 5件の fix の原因は、**日を閉じた単位とみなす旧モデルの前提が残ったこと**と、**0分の範囲を `>` と `>=` でばらばらに弾いていたこと**が中心で、計算方式の問題ではない(§1)。欠けていたのは**書かれた定義**と、**場合を自動で作って確かめるテスト**。
- 推奨: **計算方式は置き換えない**(時刻順の状態機械 + 分単位の塗りを残す)。定義をここに書き、`free-time.ts` を定義と1対1の段に分け、**参照実装との差分テストと性質テストを fast-check で足す**(§4・§5・§8)。
- 定義を書くと、仕様の文面と食い違う点・決まっていない点が6つ出た。本人判断カードにし、本人は6枚とも推奨どおりを選んだ(§7、2026-10-18)。

## 2. 仕様の形式的な定義

実装の振る舞いを、場合分けをできるだけ持たない形で書いたもの。調査時の実装(336b3c7)と一致することを §6 で確かめ、その後カード2・6の決定を反映した(以下は反映後)。`src/lib/schedules/free-time.property.test.ts` の参照実装がこの定義を分ごとにそのまま書いたもので、本体と全分一致することをテストのたびに確かめる。規則を変えるときは、この節・参照実装・本体を同じコミットで変える。

### 2.1 時間軸

- 渡された日 d₀ < d₁ < … (日付は一意。順不同で渡してよい)を、d₀ の0時を 0 とする分の数直線に置く。日 d の時刻 m は τ(d, m) = 1440·(d − d₀) + m。
- 区間はすべて半開区間 `[a, b)`。窓 U = `[0, τ(最後の日, 1440))`。
- 行の時刻は HHMM を分にする。**終了の `2359` だけは 1440(24時)**(2400 が書けないため)。

### 2.2 行の分類

1つの時刻行と、それに続く説明の行を1ブロックとする(`dayContentToScheduleItems` と同じ区切り)。

| 種類 | 条件 | 働き |
|---|---|---|
| 起床の行 | 説明が「起床」を語として含む(`isWakeActivity`) | 開始が**起床の印**。終了 ≥ 開始なら身支度の範囲を持つ |
| 消灯の行 | 説明が「消灯」を語として含み、終了 ≥ 開始(0分を含む) | `[開始, 終了)` が非自由、終了が**入眠の印** |
| 予定 E | 起床の行でなく、終了 > 開始(0分は数えない) | `[開始, 終了)` が非自由。置いた時間の集計にも使う |
| 「睡眠」の予定 N | 予定のうち、説明が「睡眠」を語として含む(`activityMatchesName`) | 睡眠の色に塗る。境目は動かさない |
| 数えない | 終了の無い予定・逆順の行 | 何もしない(保存前に弾かれるが、打鍵中の内容は解析される) |

「語として含む」は前後が行端か空白(`activityMatchesName`。目標の名前と同じ規則、カード2)。部分一致だった間は「起床時刻の見直し」「消灯前の片付け」も印として働いた。「起床。」も起床の行にならない。保存前の検査(起床の行だけ終了を省ける)も同じ判定を使う。1つの行が起床と消灯の両方を含めば、両方として働く。

### 2.3 既定の補完(前処理)

未読込の日(既定予定を書き込んだ記録 `default_schedule_applications` の無い日)で、起床の行が1つも無ければ `0700 起床` を、消灯の行が1つも無ければ `2200-2300 消灯` を書き足したものとして扱う。書き足した消灯は置いた時間の集計に入れない。これは本体の前の段で、本体は補完済みの行だけを見る(性質 P8)。スケジュール画面も `/plan` も同じ記録で判定する(カード4。それまでスケジュール画面は表示する日をすべて読込済みとして扱い、既定予定の `effective_from` より前の過去の日を補っていなかった)。

### 2.4 睡眠の核

W = 起床の印の集合、S = 入眠の印の集合として、

```
L_X(t) = max{ x ∈ X | x ≤ t }        (無ければ −∞)
眠っている(t)  ⇔  L_S(t) > L_W(t)    「t 以前の最後の印が入眠なら眠っている」
```

- 同時刻は起床が勝つ(`>` が厳密なので、`0000-0300 消灯` と `0300 起床` なら 03:00 から起きている)。
- 窓の手前: 窓の中の最初の印(同時刻の起床と入眠は入眠を先とする)が起床なら、窓の始まりより前に入眠の印が1つあったとみなす(眠った状態で窓が始まる)。そうでなければ起きた状態で始まる。印が1つも無ければ起きている。
- 同じことを区間で書くと S₀ = ⋃_{s∈S} `[s, nextW(s))`、nextW(s) = s 以後の最初の起床(無ければ窓の終わり)。

この形では、仕様の「起床が続いたり消灯が続いたりしたら2つ目以降は境目として無視する」は規則として要らない。「最後の印」(区間の形なら和集合)が自然に吸収する。日をまたぐ睡眠・1日に複数の起床・同時刻の優先も、別の場合として書く必要が無い。

### 2.5 身支度

起床の行ごとに(境目として働いたかを問わず。カード5)、

```
範囲あり:   R = [開始, 終了)
時刻だけ:   R = [w, min(w + 120, c(w)))
           c(w) = min{ max(a, w) | [a, b) ∈ E ∪ L, b > w }   (起床の時点で続いている予定があれば c(w) = w)
```

E は0分を含まない予定、L は0分を含む消灯の**記録の集合**。区間の和集合にしてから探すと0分の消灯が消え、結果が変わる(§6.3)。

### 2.6 3区分

```
SL = S₀ ∪ ⋃N                       睡眠
B  = (⋃E ∪ ⋃L ∪ ⋃R) \ SL           非自由(起きている間の予定・消灯の予定・身支度)
F  = U \ (SL ∪ B)                  自由
```

### 2.7 日ごとの出力と /plan

- `runs` は SL・B・F を日の範囲 `[τ(d,0), τ(d,1440))` で切って並べたもの。`freeMinutes` = |F ∩ 日|。`events` はその日の E。
- `/plan` の柱の中の締切の横位置は時計の時刻(締切 ÷ 24時間、時刻が無ければ 1)で、3区分を使わない(カード6。以前は日ごとの `wake` / `sleep` の間の比で決めていた)。
- 供給(締切までの自由時間)= 解析した日の |F ∩ [今, 締切)| の和 + 解析していない日数 × `EMPTY_DAY.freeMinutes`。`EMPTY_DAY` は「0時に眠っている未読込の空の日」(13時間)で、未読込の空の日が続くときの2日目以降と一致する(性質 P13)。
- 置いた時間は**3区分を使わず、名前の合う予定の記録ごとの長さの和**(重なっても、睡眠中でも数える)。

### 2.8 場合分けが残る箇所と理由

| 箇所 | 種類 | 消せるか |
|---|---|---|
| 窓の手前の推定 | 入力が有限の窓であることに内在 | 消せない。前の日を読んで影響を小さくする(`/plan` は7日前から)。7日より長く印の無い期間は確定できない |
| 身支度の2形と c(w) | 仕様に内在 | 消さない(本人の選択、カード1)。「2時間固定」にすれば時刻だけの起床 = `0700-0900 起床` の1形になり c(w) が消えるが、本人の文面「最初の予定まで」を変えることになる |
| 既定の補完 | データの来歴(既定予定の記録)に依存 | 本体からは消せる。前処理に分ける(P8) |
| 終了 `2359` = 24時 | 書式の都合 | 消せない。帰結: `2359-2359 起床` は身支度1分、`2359-2359 消灯` は非自由1分で24時から睡眠 |
| 0分の扱いの非対称(0分の消灯は印として働き身支度も切る、0分の予定は無視) | 今の実装の非対称 | 定義に明記して固定する。見える違いは起床と消灯を1行に書くような入力だけ(§6.3) |
| 「含む」の判定(起床・消灯は部分一致、睡眠は語) | 仕様が決まっていなかった | 解消(カード2で語に統一) |
| `wake` / `sleep` | 表示用で3区分と独立 | 解消(カード6で外した) |

## 3. 定義から出る、気づきにくい帰結

定義からはそうなるが、文面からは読み取りにくい振る舞い。どれも本人がカードで確認し、`decisions.md` に書いた。

- **読込済みの日を空にすると、前の日の状態が続く。** 前夜に消灯していれば、その日は次の起床まで丸ごと睡眠(自由0分)。`decisions.md` の「全部消した日は24時間起きている」は前夜に消灯が無い場合にだけ成り立つので、文面を直した(カード3)。
- 睡眠中に書いた予定は、帯では睡眠のまま(非自由にならない)。置いた時間には数える。
- 窓の最初に印の無い日が続き、その後ろに起床があると、印の無い日はすべて睡眠になる(窓の手前の推定)。後ろに日を足すと前の日が変わる唯一の経路。
- 予定を1件足すと、自由時間が増えることがある(身支度の打ち切り)。`0700 起床`・`2200-2300 消灯` の日に `0730-0740 作業` を足すと、身支度が 07:30 で切れて自由は 780分 → 860分(カード1。本人がこの帰結を受け入れた)。
- 境目として働かない起床にも身支度が付く。前日に消灯が無い日の `0900 起床` は、0〜9時が自由、9〜11時が身支度(カード5。このまま付ける)。

## 4. 方式の比較

| 観点 | (a) 区間の集合演算 | (b) 状態機械 + 分単位の塗り(段に分ける) | (c) 今の構造のまま不変条件のテストだけ足す |
|---|---|---|---|
| 正しさの保ちやすさ | §2.6 の式がそのままコードになる。ただし分類・窓の手前・0分の消灯(空区間として捨てると印が消える)は別に扱う必要があり、そこが誤りの出どころだったことは変わらない | 睡眠の核は「最後の印」の走査、優先順位は塗る順(睡眠 → 非自由 → 自由)、同時刻の規則は比較関数の1か所 | 構造の検査(合計24時間など)だけでは「形は正しいが睡眠の区間が違う」が通る。参照実装との差分テストを足せば (b) と同じ守りになる |
| 読みやすさ | 式は定義そのもの。区間の正規化・差・交わりの補助(試作で約45行)を持つ | 今のコードがほぼこれ。補完・分類 → 印と区間 → 塗り → 日ごとに切る、の段に分ければ定義と1対1 | 変わらない(今の `analyzeDays` は1関数に全段が入っている) |
| 日をまたぐ扱い | 絶対時刻で自然 | 全日の分の配列で自然(今と同じ) | 今と同じ |
| /plan との共有 | 供給を F ∩ [今, 締切) で直接求められる。置いた時間は記録ごとなので別 | `runs` と `freeMinutesBetween` を今どおり共有。全体の時間軸の問い合わせも足せる | 今と同じ |
| 性能(Node、128日 / 250日、30回の中央値) | 2.2ms / 6.3ms(素朴な試作) | 3.0ms / 5.4ms(今の実装) | 同左 |
| 移行の危険 | `analyzeDays` の書き直し。差分テストが守る | 小さい。差分テストが守る | 無い |

性能はどの方式でも打鍵ごとの再計算に十分で、選ぶ理由にならない(astra の別の測定でも 127日で中央値 2.41ms)。

## 5. 性質の一覧とテスト方針

### 5.1 性質

「今の実装」は調査時の試作での実測(fast-check または自前の生成器、件数は各性質のランダム入力数)。P1〜P13(P11' を除く)は `src/lib/schedules/free-time.property.test.ts` に置いた(各300件、P3 は500件)。

| # | 性質 | 今の実装 |
|---|---|---|
| P1 | 各日の `runs` が `[0, 1440)` を隙間・重なり無く覆い、隣り合う run は種類が違う(睡眠+非自由+自由 = 24時間) | 成立(2,000件) |
| P2 | `freeMinutes` = 自由の run の和。`freeMinutesBetween(a,c) = (a,b) + (b,c)` | 成立(1,500件) |
| P3 | 参照実装(§5.2)と全分一致 | 成立(約10,500件 + fast-check 1,000件) |
| P4 | ブロック(時刻行と続きの説明行)の順序に依存しない | 成立(4,000件) |
| P5 | 日を渡す順序・全日付の平行移動に依存しない | 成立(各1,500件) |
| P6 | 後ろに日を足しても、それまでの日は変わらない(元の窓に印が1つでもあるとき) | 成立(4,000件) |
| P7 | 前に日を足しても、印のある最初の日より後の日は変わらない | 成立(4,000件) |
| P8 | 未読込の日の結果 = 既定の行を書き足した読込済みの日の結果 | 成立(4,000件) |
| P9 | 同じ行を重ねても、普通の予定を隣り合う2つに割っても、帯は変わらない | 成立(各1,500件) |
| P10 | 印でない予定を足しても、睡眠の核は変わらない | 成立(1,500件) |
| P11 | 予定を1件足して自由になる分は、時刻だけの起床から2時間の中にしか無い(弱めた単調性) | 成立(1,500件) |
| P11' | 予定を1件足すと、どの日の自由時間も増えない | **不成立**(身支度の打ち切り。本人の選択で残すので置かない。2時間固定なら成立: 試作で 0/2,000) |
| P12 | 締切を遅くすると供給は減らない | 成立(1,500件) |
| P13 | 未読込の空の日が続くとき、2日目以降は `EMPTY_DAY` と一致し、1日目は0時に眠っていれば一致・起きていれば多い | 成立(3,000件) |

性質として置かないもの(偽なので): 「起床が続くと2行目は何も変えない」(身支度が付く)/「1日だけの解析 = 連続解析の同じ日」(窓の手前が違う)/「予定を重ねても置いた時間は変わらない」(記録ごとの和)。P6 は元の窓に印があるときに限る(無いと窓の手前の推定が後ろの日から決まる)。

### 5.2 テストの作り方

- **生成器**は文字列ではなく構造を作って文字列に直す: 日 = `{ loaded, lines }`、行 = `{ start, end, label }`。
  - 時刻は30分刻みを主に、端の値(0000・2359・0700・2200・2300)と任意の分を混ぜる。
  - 終了は「無し・同時刻・2359・逆順・正の長さ」から選ぶ。
  - 説明は、印(`起床`・`消灯`・`起床 発送`・`BM 読書 消灯`)、`睡眠`、普通の予定、紛らわしい語(`睡眠薬を買う`・`消灯前の片付け`・`起床時刻の見直し`・`起床。`・`起床 消灯`)から選ぶ。
  - 1〜5日、loaded は7割。
- **参照実装**は定義を分ごとにそのまま判定する素朴なもの(約40行): 各分 t で L_S(t) > L_W(t) と区間への所属を調べ、§2.6 の式で種類を決める。遅いが、読めば正しさが分かる。テストファイルの中に置く。
- **入力の解釈は手書きの期待値で確かめる。** 参照実装は予定テキストではなく生成器の行の構造から直接分類するので、本体のテキストの解釈とは独立しているが、複数行の説明のようなテキスト固有の解釈は生成器が作らない。複数行の説明・空白と句読点・`起床 睡眠`・`起床 消灯`・逆順の起床・`2359-2359` は例のテストで固定する。
- **fast-check を devDependency に入れる(入れた)。** 理由は試作で縮小が実際に役立ったこと: 単調性の反例を `[[{"loaded":false,"lines":[]}],0,"0331-0701 作業"]`(未読込の空の日に、既定の 07:00 起床をまたぐ予定を1件)まで自動で縮めた(2,000件中183件目で発見、60ms)。自前の生成器と縮小器は約60行かかり、生成器を変えるたびに縮小も書き直しになる。seed と path で再現できる。本番のバンドルには乗らない(fast-check 4.10.2 で試用)。
- **実行時間**: 参照実装との一致 1,000件で 383ms。`npm test` では各性質 300〜500件にする。
- **回帰例**: 過去の fix で壊れた8点の入力と、fast-check が見つけた反例は例のテストとして固定する。同時刻の規則(`0000-0300 消灯` + `0300 起床`)、7日より長く印の無い期間、`/plan` の読込範囲の外の 420分差(§6.2)は、今のテストに無いので足す。

## 8. 推奨する方式と、その推奨が覆る条件

**推奨: (b)。** 計算方式は今の状態機械と分単位の塗りのまま。定義(§2)を正として、コードとテストをそれに合わせる。

3. `free-time.ts` を「補完・分類 → 印と区間 → 塗り → 日ごとに切る」の段に分け、0分の範囲の判定を1か所にまとめる。振る舞いは変えない(2 のテストが守る)。

理由: 5件の fix の原因は計算方式ではなく、書かれた定義が無いことと、テストが場合を作らないことだった(§1)。今の実装は既に定義と一致しているので、書き直しの対価(移行の危険)に見合う利得が実測から出ない(§4)。区間の集合演算の利点(式がそのままコードになる)は、段に分けた (b) と参照実装のテストでおおむね得られる。

推奨が覆る条件:

- **(a) 区間の集合演算に移る:** 実機(スマホ・ノート)で、読み込む日数が増えて打鍵ごとの再計算が遅延の主因になったとき。または、区間をまたぐ問い合わせ(まとまった枠・日をまたぐ空きの検索など)が `/plan` の主な機能になったとき。
- **(c) テストを足すだけで止める:** 手順2の後、カードの反映も含めて当面 `free-time.ts` を変える予定が無いなら、手順3(段に分ける)は次に仕様を変えるときまで延ばしてよい。守りの大半は手順2で得られる。
- どの方式でも解決しないこと: 「7日より前の状態も常に正確」「読む範囲を変えても結果が変わらない」を要件にするなら、計算方式ではなく、過去の状態を確定して持ち越す仕組み(初期状態を引数で渡すなど)が要る。
