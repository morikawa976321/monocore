# drain報告板・AIブリッジ・関連ボード

いつ読むか: taskbox drainの報告板（monocore `/drain`）やAIブリッジ（スキル経由の読み書き）、inbox/projectボードの実装・変更をするとき。

## drain報告板の設計方針の変遷（最終形は2026-09-12時点）

1. **機械値だけで作る（2026-08-12判断）**: `/drain` に出す「何をして／どうなったか」は、ラッパー（`drain.ps1`）が持つ機械値と `traces/<task-id>.json` の `steps[]`（当時は `{desc, note}` の組）だけで組み立てる方針を採用し、drainセッションに構造化ブロックを出させる案は採らなかった。理由: 無人経路に自己申告を増やさない（taskboxは「完了は自己申告で決めない、機械判定を根拠にする」で一貫）。非対称性（薄い→厚いは後から足せるが、逆に一度増やした自己申告を減らすのは面倒）から、まず薄い側を選んだ。前提事実: `drain.log` はファイルとして読み返す必要が無く、同じ内容は `drain.ps1` が `$out` としてメモリに持っている（ログ側は7日ローテーションと並行書き込みがある）。

2. **4点だけに絞る（2026-08-15判断）**: 板に求めるのは「①なにをやったか／②うまくいったか・いかなかったか／③うまくいかなかった場合その理由／④想定外に発生・発見したこと」の4点だけ。理由: 板は「どの枠を掘り下げるかを決めるための面」であって作業ログではなく、詳細が要るときは本人がセッションを開いて聞ける。前提: ④「想定外」だけは運ぶ経路が無かった（traceの `notes` を投入ペイロードに入れていなかった）ため、書かれていても画面に出ていなかった。

3. **①②を1文へ畳む（2026-08-30改訂）**: 本人指示「各タスクは何のために何をしてどうなった、というレベルまで要約していい。私の判断がいる点やトラブルはいまのまましっかり記録する感じで」。①何をやったか＋②成否を1タスク1文（目安120字・上限200字、`summary` フィールド）へ畳み、**③つまずき（`failures[]`）と④想定外（`notes`、用途に「本人の判断が要る点」を明示追加）は畳まない**。線引きは「縮めるのは平常運転の記述だけで、本人が動く必要のあるものは縮めない」。`steps[]` は集計用として残るが画面には出さない。板の報告が長すぎるという指摘はこれで2回目（2026-08-15に続き）で、項目数を絞っても1項目あたりの行数が残っていたための再改訂。

4. **タスク別詳細の表示を停止（2026-09-12判断、現時点の最新形）**: `traces` 由来のタスク別詳細（summary/failures/notes/委譲）の表示自体をやめ、当面はオーケストレーターの報告全文（`report_text`）だけで足りるとした。taskbox側は `drain_runs.tasks` へ常に空配列を送り、monocore側も表示コードを削除（`traces/*.json` 自体の記録・集計用途は変更なし）。本人の言葉で「いったん」「なんなら報告全文すらもなくすかも」とあり、最終形として確定したものではない。同日、traces の `steps[]` キー自体も使い道が無くなり廃止されている。

## drain板の保持件数とスキップカード統合（2026-09-10〜11決定）

`monocore\scripts\upsert-drain-run.mjs` は `drain_runs` へupsertするたびに `pruneOlderThanKeep(supabase, DRAIN_RUNS_KEEP)` を実行し、`started_at` 降順でKEEP件目より古い行を削除する（フロント `monocore\src\app\drain\page.tsx` も `DRAIN_RUNS_LIST_LIMIT` で直近分のみ取得しページネーション無し）。行数は元々青天井ではなく常にKEEP件で頭打ち（2026-09-10までは40件）。4回/日運用では40件≒直近10日分が見えていたが、1時間おき運用では40件≒直近1.7日分に縮む。

決定の経緯:
1. （2026-09-10）当初方針: 連続スキップを1カードにまとめたい。
2. （2026-09-11前半）保持件数を40から**48**（1時間おき24枠の2日分）へ引き上げるだけで十分と判断し、統合UIは見送った。
3. （2026-09-11後半）実運用で08:00〜14:00の7回が実際に連続スキップになり、48枚中7枚を1つの事象が占める実例が出たため、**統合UIを実装することに決定を戻した**。

現在の形（実装済み）: 保持件数 `DRAIN_RUNS_KEEP` / `DRAIN_RUNS_LIST_LIMIT` = 48。`monocore/src/lib/drain/group-runs.ts` の `groupDrainRuns()` が、一覧（started_at降順）で隣接する2件以上の `outcome === 'skipped'` をグループ化する純関数（孤立した1件はそのまま個別カード）。**`crashed` は畳まない**（畳んで埋もれさせると異常の合図を見落とすため）。表示は `DrainRunGroupCard`（時刻範囲+件数の要約、展開すると中身は既存の `DrainRunCard` をそのまま並べる）。

## AIブリッジの結線方式と権限モデル（2026-07-20決定）

Phase 3着手前の設計判断（Phase 3自体はその後凍結されたが、権限モデルは自律実行一般に転用可能）。

- **Realtimeは不要。taskboxのdrainと同様のポーリングでよい**（本人決定）。2026-07-14の「メッセージバスはSupabase Realtime(確定)」を撤回。常駐WebSocketとその再接続処理が不要になる。
- **破壊的操作か低リスク操作かをLLM側で判断し、前者は2ターン確認、後者はそのまま実行**（本人決定）。操作のリスクは操作種別だけでは決まらない（同じ削除でもスクラッチとengineでは別物）ため、文脈を見る層は必要。
- **LLM判断はラチェット（一方向）にする**: 自動実行可の範囲は決定論的なルール（LLMの外）で定義し、LLMは許可リスト内の操作を2ターンへ引き上げることはできるが、確認対象を直接実行へ引き下げることはできない。理由: 判定するのは実行したがっている本人と同じコンテキストであり、直前に読んだノート・handover・外部テキストに汚染されうる。
- **2ターン目は再計画ではなく事前固定した操作の実行にする**。確認レコードに実際のSQL/コマンド/パラメータを保存し、承認時はそれを実行するだけにする。「古いファイルを消す?」→「はい」→別セッションが"古い"を解釈し直す、という作りは事故（incidents.md「疎通確認のつもりの空配列でデータ削除」）と同型になる。ポーリング型でセッションが毎回別プロセスになる以上、実装上も必須。

設計の正はmonocoreリポジトリの `docs/design.md`。

## AI編集権スキル（M1、2026-07-17完了）

Claude Codeセッションから会話でmonocoreを読み書きできる。**対応する対象はschedules（予定）のみ** — tasks/knowledge/projectsはページ・DBテーブル・スキルコマンドごと完全削除済み（`monocore.py` と `SKILL.md` に残存が無いことは2026-07-30に裏取り済み）。Claudeアプリからの予定挿入は使用中（2026-08-06本人申告）。

所在と機能:
- スキル: `~/.claude/skills/monocore/`（`SKILL.md` + `monocore.py`。Python標準ライブラリのみ。`~/.claude/skills/` はgit管理外という既知の制約あり）
- 認証: service role key。置き場は `%USERPROFILE%\.monocore\config.json`（monocoreリポジトリ外・平文コミット禁止）
- 機能: list/show/add/append/update と `set-status`（{active,completed,deleted}切替＝論理削除と復元。`--dry-run` で対象titleを表示）。楽観ロック（read時 `updated_at` の条件付きPATCH）・`updated_by='agent'` は書き込み系共通。
- **既定環境は `remote`（本番）**。当初は「本番を壊さない安全策」として `local` を既定にしていたが、localはラップトップ上の開発用砂場で、ユーザーのスマホ・ブラウザが見る本番とは別物のため**AI編集が実データに一切反映されない設計ミス**だった（本人指摘で修正）。localは開発・検証専用。**教訓: 「本番データを壊さない安全策」と「機能の既定動作」を同じフラグに乗せると、安全のつもりが機能そのものを殺す。既定値は実ユースケースを満たすかで決める。**

採用した設計（案A: service_role専用RPC）: service_roleのJWTには `sub` が無く `auth.uid()` がNULLになるため、既存のユーザーセッション用RPCがそのまま使えない（詳細はsupabase-postgrest-pitfalls.md「service role keyとauth.uid()は両立しない」）。3案から**案A＝service_role専用RPC `replace_schedules_for_day_as(p_user_id, ...)` を加算的migrationで新設**を採用（既存RPCは変更していない）。

- 案B（JWT secretで `sub` 入りトークンを自前発行）却下: 署名鍵の所持＝任意ユーザーへのなりすまし能力であり、service key限定方針に反しリスクが高い。
- 案C（RPC非使用でDELETE+INSERTを再実装）却下: 「その日を丸ごと安全に置換する」アトミック性をスキル側で二重実装することになり、2026-03-25に修正した2デバイス編集でのデータ喪失と同種の競合リスクを負う。

セキュリティ要点: この関数はSECURITY DEFINERかつ引数でuser_idを受け取り認証チェックを持たないため、Postgres既定のPUBLIC EXECUTEのままだと**anonが任意ユーザーの予定を破壊できる**。`REVOKE ALL FROM PUBLIC, anon, authenticated` → `GRANT EXECUTE TO service_role` が必須（実装済み・本番でanon/publishable keyが401になることを実機確認済み）。今後同種のservice_role専用RPCを追加する際も同じREVOKEを必ず付けること。

AIマーク粒度は日単位の粗さを許容: 置換方式RPCはその日を削除→再挿入するため、AIが1件足しただけでその日の既存予定（人間が入れたもの）まで `updated_by='agent'` になる。(a)許容 (b)`p_items` 各要素に `updated_by` を持たせRPCが引き継ぐ (c)schedulesだけマーク非表示 のうち**(a)を採用**。

## inboxへの書き込みはREST直叩き（2026-08-13運用知見）

Claudeスキル `monocore` の `monocore.py` は**schedules専用**で、inboxのコマンドを持たない（`inbox` の語がソースに1つも無い）。「monocoreのinboxに追記して」という指示に対して、スキルを開いても手段が無い。

書き方: `inboxes` は `user_id` 主キーの**1ユーザー1行・単一TEXT blob**（`content`）なので、REST（`/rest/v1/inboxes`）でGET→文字列連結→PATCHの**read-modify-write**になる。追記APIは無い。実施時に必要だったもの:

- バックアップを先に取る（blobを丸ごと差し替えるため、失敗すると全損しうる）
- 冪等マーカー（追記済みの目印になる文字列を `content` に含むかで判定。再実行での二重追記を防ぐ）
- 行数チェック（GETが1行でなければ中止）と読み戻し検証（文字数とマーカー）
- 本文をログに出さない — inboxには認証情報が混在していた実績がある。長さだけ出す。
- 鍵の扱いはreportsの同期と同じ規約に従う: スクリプト側が `~/.monocore/config.json` を自分で読み、値をコマンドラインにも出力にも出さない。

副次的な事実: 実行時点（2026-08-13）の `inboxes.content` は2163文字・117行。2026-07-21の棚卸し時点の266行・10,672字から大きく縮んでいる。
