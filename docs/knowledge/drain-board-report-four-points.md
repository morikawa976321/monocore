# drain報告板に載せるのは4点だけ（2026-08-15判断）

## 選択

本人の言葉は「drain板の報告がやや丁寧すぎる。具体的な実装内容などはセッションで個別に聞く」。板に求めるのは次の4点だけである:

1. なにをやったか
2. うまくいったか・いかなかったか
3. うまくいかなかった場合、その理由はなにか
4. タスク遂行中に想定外に発生・発見したこと

## 理由

板は**どの枠を掘り下げるかを決めるための面**であって、作業ログではない。詳細が要るときは本人がセッションを開いて聞けるので、板に詳細を置く価値は薄く、長い本文はむしろ4点を埋もれさせる。プロジェクトカードで2日続けて「長すぎる」と指摘され上限を規約化したのと同じ判断が、drain板にも及んだ形。

## 前提として確認した事実

- 板の本文は `traces/<task-id>.json` から機械的に組まれる（[[drain-board-machine-values-only]]）ので、直す場所は表示側ではなく**トレースの書き方の規約**である。
- 4点のうち「想定外」だけは運ぶ経路が無かった（traceの `notes` を投入ペイロードに入れていなかった）ため、書かれていても画面に出ていなかった。

## 粒度の改訂（2026-08-30）: ①②は1タスク1文へ畳む

本人の指示: 「drain板の報告も長すぎる。各タスクは何のために何をしてどうなった、というレベルまで要約していい。私の判断がいる点やトラブルはいまのまましっかり記録する感じで。」

- 4点のうち **①何をやったか と ②成否 を1文へ畳む**。工程を3〜6行並べるのをやめ、タスク1件＝要約1文にする。
- **③つまずき（`failures[]`）と ④想定外（`notes`）は畳まない。** `notes` の用途に「本人の判断が要る点」を明示的に足した。
- 線引きは「**縮めるのは平常運転の記述だけで、本人が動く必要のあるものは縮めない**」。
- 実装は `traces/<task-id>.json` に `summary`（目安120字・上限200字）を足し、板がそれを本文にする形。`steps[]` は集計用の記録として残るが画面には出ない（machine-values-onlyの構造は不変）。

板の報告が長すぎるという指摘はこれで2回目（2026-08-15「やや丁寧すぎる」に続く）。前回は載せる項目を4点に絞る形で答えたが、項目を絞っても1項目あたりの行数が残っていた。
