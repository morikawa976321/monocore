# reportsミラー・newsスクレイピング統合

いつ読むか: `mf/reports/` のmonocoreミラー（`/reports`）や、news_scrapingの統合（`/news`、`monocore/scraper/`）を実装・変更するとき。

## reportsミラーの設計方針

### スマホ閲覧はmonocore経由の読み取り専用ミラー（2026-08-09決定）

`mf/reports/`（30本・約1.2MB）をスマホから読みたいという要求に対し、monocoreに読み取り専用のミラーを作る方式で確定。

- **全件同期**（ホワイトリストによる選別はしない）。
- **reportsのコミットとmonocoreへのupsertをセットで走らせる**（reports/CLAUDE.mdの「作ったらその場でコミット」規約に結線し、ミラーが腐るのを防ぐ）。
- 型は `project_cards` と同じ「正はローカル／service_roleでslug単位upsert／画面はSELECTのみ」。

選んだ理由: 実体は「ラップトップがスリープ中の電車・ベッドで読む」なので24/7可用性が必須。Tailscale+ローカルHTTPはスリープで死に、GitHub private repoはreports規約が禁止している。クラウドDBしか残らず、それは既にある。閲覧専用なので双方向同期の難所（schedulesが日単位版管理で払ったコスト）が丸ごと不要。

面追加基準（「本当に毎日使うか」）への回答: 本人「レポートは毎日ではないが、電車内で確実に使う。問題ない」。頻度が毎日でなくても、使う場面が具体的に特定できているなら足してよい、という基準の運用。過去に死んだ4面はすべて入力を伴う面だったが、今回は読み取り専用の導出物のため、使われなくなってもテーブルとページを消すだけで損失が出ない。

### 同期の2原則（2026-08-09判断、reports以外のミラーにも適用）

1. **同期は「集合の一致」であってupsertではない。** ローカルをスキャンしてupsertし、DBにあってローカルに無いslugはdeleteする。upsertだけだと消したもの・archiveへ移したもの・リネームしたものがミラーに残り続け、「ローカルが正」という原則が破れる。
2. **導出物は単一形式でのみ持つ。** 同じ内容をmdとHTMLの両方で持つような二重保持をしない。片方を捨てて失う機能（例: 本文の全文検索）は、カラムを足すのではなく別の手段で代替する（例: 検索対象をタイトルと見出しに絞り、本文内はブラウザのページ内検索に任せる）。

付随して確認した事実: 容量は当面この設計の律速にならない（reportsの実績は約1MB/月、context-engine全体でも377ノート1.18MB、Supabase無料枠500MBに対して桁が違う。PostgresのTOASTが2KB超のtext列を自動圧縮する）。上の2原則は容量対策ではなく正しさのために採る。

### 3点目: ローカル文書間の相対リンクは同期時に書き換える（2026-08-09）

ミラー元のコンテンツ同士が相対リンクで参照し合っている場合（例: `design_language_unification_briefing.md` から `[本文](product_sales_roadmap.md)`）、そのまま変換すると `<a href="product_sales_roadmap.md">` になり、ミラー先のURL構造（`/reports/product_sales_roadmap`、拡張子なし）と食い違って404になる。スマホでレポートを読みながら関連レポートへ飛ぶ、というまさにこの機能が想定する使い方で踏む。

対処: 同期スクリプト側で変換パイプラインにリンク書き換えのステップを挟む。対象は「相対パスかつ`.md`で終わるリンク」のみ（外部URL・絶対パス・アンカーのみは対象外）。書き換え先のslugが**同期対象に実在する場合のみ**書き換える（`/reports/<slug>`）。archiveへ移動済み・削除済みなど同期対象外を指すリンクは、書き換えても別の404になるだけなので元のまま残す。判定に使う「同期対象slugの集合」は、その回の同期でローカルから読み取ったファイル一覧から作る（DB問い合わせ不要）。

一般則: ローカルの複数ファイルを1つのミラー先（URL構造の異なる別システム）へ同期するとき、ファイル間の相互参照（相対リンク）は変換漏れに気づきにくい。該当ファイルが少数でも（実例では32本中1本）、実際に踏む導線を塞がないためには「壊れたリンクを放置しない」対処を同期パイプラインに組み込む方が、個別の記事を手で直すより保守コストが低い。

### markdown→HTML変換の罠: rehype-sanitizeのclobberPrefixが見出しidをズラす（2026-08-09実測）

`/reports` 実装で `rehype-slug`（見出しに`id`を振る）→`rehype-sanitize`（既定スキーマでサニタイズ）という定番の組み合わせを使ったところ、目次(toc)のanchorとbody_html中の実際の`id`がズレて目次リンクが機能しない状態になった。

原因: `rehype-sanitize`の`defaultSchema`は`id`属性そのものは`tagNames`の`*`許可リストに含めており削除はしない。しかし`clobberPrefix`（既定値`"user-content-"`）により、DOMクロバリング対策として全てのid/name属性の値へ接頭辞を自動で足す（例: `id="見出し"` → `id="user-content-見出し"`）。rehype-slugが振った素のidをtoc抽出に使うと、sanitize後のbody_html中のidと食い違う。見た目上「idが消える」わけではなく「idの値が書き換わる」ので、`defaultSchema.tagNames`や`attributes['*']`をNode REPLで確認しただけでは気づけない（実際に両方の値を突き合わせて初めて分かる）。

対処: 自分のmarkdownしか扱わない（外部ユーザー入力を受け付けない）前提なら、DOMクロバリング対策自体が不要なので無効化してよい。

```js
import { defaultSchema } from 'rehype-sanitize'
const schema = structuredClone(defaultSchema)
schema.clobberPrefix = ''
```

これでrehype-slugが振った素のidがそのままbody_htmlに残り、toc抽出のタイミング（sanitize前でもtoc-only用途なら後でも）によらず一致する。外部ユーザー入力を扱う場合はこの対処は不適切（クロバリング対策を無効化することになるため）。

一般則: `rehype-sanitize`を使うときは`defaultSchema`の中身を`tagNames`/`attributes`だけでなく`clobberPrefix`/`clobber`/`ancestors`も含めて確認する。「属性が許可リストに載っているか」だけでは、値が書き換えられるケースを見落とす。

### 運用知見: 索引にだけ書いた警告はミラーに届かない（2026-08-12）

`mf/reports/_index.md` は「今も生きているか」を書く場所として運用しているが、monocoreの`/reports`ミラー（スマホから読む面）は `_index.md` と `CLAUDE.md` を同期対象から除外している（`scripts/reports-payload.mjs` の `EXCLUDED_FILENAMES`）。結果、索引に警告を書く運用は、レポート本文を直接開く読み手に対して機能しない。

実例（2026-08-12検出）: `hci_core5_summaries.md` は冒頭が今も「結論: 「優しい嘘 × well-being」の空白は全文レベルの精査でも生き残った」のままで、この線が没になったことは本文に一文字も無い。索引には2026-08-09から警告が書かれていたが、スマホから開けば警告なしで死んだ結論に当たる状態が続いていた。

規則: 「結論が死んだ」型の警告は、索引ではなく本文の冒頭に書く。索引側の注記は、本文に書いた警告への案内か、複数レポートにまたがる関係の記述にとどめる。索引は「どれを読むか」を決める道具であって、読むと決めた後の読み手はもう索引を見ていない。同型の注意: `archive/` 配下も同期対象外なので、archiveへ退避したレポートはスマホから引けない。

## news_scrapingのmonocore統合（2026-08-14）

### 前史: 統合前の状態（LLM要約の実装と破棄、記事選別の打ち切り）

`mf/news_scraping` は統合前、すでに完成し日々活用していたツールだった（構想・開発中ではなく稼働中）。動機の出発点は「大量のニュースを自分で取捨し読むのが面倒になってきた」ことで、あらかじめLLMで取捨選択・要約する機能の追加を検討していた（ローカルLLMまたはagy想定）。

**LLM要約は実装されたが破棄された（実装2026-07-20→破棄2026-07-21）**。実装内容: 新着記事にローカルllama-serverで日本語1〜2文の要約を付与し記事一覧に表示、定時実行フローに組込済み、LLMが落ちていれば要約なしで従来どおり動作、要約の入力はRSSのdescription（記事本文は別途取得しない）。技術的には完遂していたが、成果物がユーザーの気に入らず変更ごと破棄された。自律実行ベースラインテスト第1号でもあり、失敗モードは実行能力ではなく意図の推定だった。実装時の運用知見: `C:\Users\tm976\mf\duocad\docs\knowledge\local-llm-reasoning-empty-content.md`。

取捨選択（興味に基づく記事選別）は未着手のまま2026-07-21のクローズに含めて打ち切った。ユーザーの興味プロファイルは旧リポジトリに書き込まない方針だった（GitHubの公開リモートを持つため）。monocoreのprojectレコードはこの経緯を記録した上で2026-07-17に削除済み。

### 決定: 記事保存をJSONLからSupabaseへ、閲覧面は/newsに一本化

`mf/news_scraping` の記事データを `static/articles.jsonl` から monocore の Supabase（`public.articles`）へ移す方針を本人が決定した。

1. **閲覧面はmonocore `/news` に一本化する。** LAN内限定のFlaskアプリ（`app.py`・`templates/`・タスク`NewsScraping_FlaskWeb`）は撤去する。選んだ理由は「スマホから読めるようになる／UIを2つ保守しない／常駐プロセスが1本減る」。対案（Flask併存・DB移行だけで面は作らない）は不採用。
2. **保持は現状踏襲**（`published` が8日より古い行を毎回物理削除）。「DBには蓄積して表示側だけ直近N日に絞る」（年2万行・数MBで無料枠に収まり、RSS再出現による重複復活も消える）を推奨として提示したが不採用（理由は述べられていない）。

派生した設計上の事実: `articles` はmonocoreで唯一「正がDBにあり、かつ人間が書いたものでもない」テーブルになる。既存の導出物3つ（`reports` / `project_cards` / `drain_runs`）は消えても再生成できるが、RSSは過去記事を配らないので `articles` は消えたら戻らない。保持8日を選んだため、失われうる最大値は「8日以内に読み逃した記事」。

### 判断: リポジトリごと吸収、スクレーパーはPythonのまま（書き直さない）

`mf/news_scraping` はリポジトリごとmonocoreに吸収してフォルダを削除し（スクレイピングロジックもmonocore内、移設先 `monocore/scraper/`）、**ただしスクレーパーはPythonのまま移す。nodeへの書き直しはしない**。当初は「monocoreに入れる＝nodeに揃える」と束ねて提案されたが、本人の「pythonwのまま使えないのか」という問いで分離された。

理由（一般化できる形）: 得たかったもの（フォルダをなくす・一箇所に統合する・スキーマとライターを同じコミットに乗せる）はすべて言語に依存しない。言語を変えて増える利益は「venv/pytestが消える」「Supabase読み書きを既存のnode資産で書ける」の2点だけで、その対価は「既に直したバグの塊を買い直すこと」（エンコーディングのフォールバック、OGPの属性順2パターン、`published_parsed`と`updated_parsed`の優先順、JST変換、RDFフィードの解釈）と「一度解いた実行環境の問題を解き直すこと」（`pythonw.exe`によるウィンドウレス起動。node.exeはコンソールアプリなので毎時ウィンドウが点滅する）。画面上は何も変わらないのに下振れだけがある取引になるので採らない。移設のコストはpolyglotリポジトリになること（venv・requirements・pytestがmonocoreに入る）だけで、これは受け入れる。

併せて決めた歯止め: monocoreの責務が「人間向けの窓口＋導出物の受け皿」から「外界から取り込むワーカーを持つ」に広がるため、`docs/design.md` に1行の方針を追加した——**収集ジョブをmonocoreに置いてよいのは、その出力をmonocoreの面が表示する場合に限る。面を持たない収集はtaskboxの管轄。**

### 事実: 移設元リポジトリは完全削除（archiveではない）

移設完了に伴い、`mf/news_scraping` はローカルフォルダもGitHubリポジトリ（private）も本人が完全に削除した。AI側は「移植元として数ヶ月は参照価値があるのでarchive」を勧めていたが採られなかった。

効いてくるところ: 移設前のコミット履歴はもう存在しない。`monocore/scraper/` のコードが今の形になっている理由（OGPの属性順2パターン、`published_parsed`と`updated_parsed`の優先順、エンコーディングのフォールバック、XSS対策のURL検査など）は、コミットログではなくmonocore内のコメントとREADMEにしか残っていない。移設時にコメントとして書き写した範囲が、そのまま残った全部である。したがってscraperに手を入れるとき、「昔なぜこう書いたか」をgitで遡ることはできない。コードのコメントが唯一の根拠であり、消すと復元できない。
