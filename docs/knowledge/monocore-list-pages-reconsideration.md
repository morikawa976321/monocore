# 決定: monocoreの一覧ページ(tasks/knowledge)を廃止(2026-07-17提起、2026-07-20時点で廃止済みを確認)

## 決定に至った検討(2026-07-17時点の原記録)

- projectsページ廃止の直後、ユーザーが提起: **毎日把握すべき情報はごく一部で、大半はengineに置いてチャットからAIに探させ・予約までさせた方がよいのではないか**。面として残す価値があるのは「その瞬間読みたくて、解釈の余地がない単体完結の情報(かつ高頻度)」(例: 筋トレメニュー)だけかもしれない、という問い。
- これは[[monocore-user-gateway-decision]]の否定ではなく先鋭化(窓口≠倉庫)。ただし2026-07-14の「monocoreの中身は人間が頻繁に読みたい生きたデータ」という前提認識を、実利用データ(タスク31件が3〜4月から滞留等)に基づき修正する動きでもある。
- Claude側の分析で出た判断基準の候補: 「高頻度・即読」よりも**「ブリッジ(ラップトップ)が寝ている時にモバイルで必要か」**が本質。ラップトップ前ではAI(Claude Code)が同期的に使えるためengineで足り、モバイル+ブリッジ稼働中はチャットで足り、**モバイル+ブリッジ睡眠中だけがSupabase直結の面を要求する**(電車問題と同型のロジック)。

## 決着(2026-07-20確認)

- tasks/knowledgeページは廃止済み。ユーザー確認: **テーブルもスキルも全部消した**(2026-07-20)。[[monocore-projects-removal]]と同一パターン(ページ・DBテーブル・スキルコマンドの完全削除)がtasks/knowledgeにも適用された。**2026-07-30に確認済み**: `AGENTS.md` `README.md` には残存言及なし。`docs/monocore-v2-design-draft.md` にのみ knowledge の記述が残るが、これは設計時点の履歴文書なので許容する。
- これによりmonocoreの面はSchedule(+Inbox)中心に縮小し、[[monocore-projects-removal]]と同型のパターン(設計上の建前より計測された行動を優先して面を畳む)がtasks/knowledgeにも適用された。
- 関連する機能要望の失効整理は実施済み（機能要望3件・既知バグ3件を2026-07-20に全破棄。追跡打ち切りであり解決ではない）。
