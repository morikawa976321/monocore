# monocoreのフェーズ計画を捨てる（2026-08-06）

2026-08-06統合: 旧 `monocore-design-draft-realigned`（ドラフト乖離6件の記録）を吸収。廃止理由2「表は腐っても誰も気づかなかった」の唯一の証拠であり、対象文書（v2設計ドラフト）も既に存在しないため。

## 選択

monocore の `docs/monocore-v2-design-draft.md`（Phase 1〜4のロードマップ）を廃止し、内容を3つに割った:

- **実装済みの構造・ルール** → `README.md`（ルート・テーブル・投入経路・書き込み規約・禁止事項）
- **実装が守る制約と、まだ決まっていないこと** → `docs/design.md`（新設）
- **判断とその理由** → engine（ここ）

起点はユーザーの指摘「実装した内容と実装する内容が混ざっている。実装した内容はREADMEでいい。実装する予定の内容は現時点では実はほとんど何も決まっていない気がする」。

## 理由

**フェーズ表は一度も当たっていない。**

| 実装されたもの | 由来 | 結果 |
| --- | --- | --- |
| Phase 1 AI編集権スキル（7/17） | フェーズ表 | 稼働中（7/20の不使用判定は8/6に撤回、予定挿入は使用中） |
| Phase 2 要注意タスクパネル（7/17） | フェーズ表 | 同日撤回・削除（[[monocore-due-tasks-panel-removal]]） |
| プロジェクト板（8/3〜） | 朝の文脈回復コストという実地の痛み | 稼働中 |
| schedulesの日別メモ欄（8/5） | 実地の痛み・表になし | 稼働中 |
| メモ欄とtaskboxの回収連携（8/5） | 実地の痛み・表になし | 稼働中 |

1. **表は着手順を予測できなかった。** 稼働中の5件のうち3件は表に存在せず、表にあるPhase 3を飛ばしてPhase 4相当が先に入った。
2. **表は腐っても誰も気づかなかった。** 2026-07-18を最後に更新が止まり、その後の決定6件を1件も反映しないまま放置された（証拠は下記の乖離記録）。

**当初の主論拠は「フェーズ表から作ったものは全部死に、生きているものは全部表の外から来た」だったが、同日中にPhase 1の不使用判定が撤回されたため取り下げた**（判断当時に依拠していた事実が数時間で崩れた例 — usage-verdicts-need-an-observation-window）。廃止の結論は上の2点で維持される。

**一般化: 実装が参照しない計画表は、腐っても誰も気づかない。** 実装の駆動が「毎日の運用で痛みが出た箇所」である以上、計画表は予測にも拘束にもなっておらず、維持コストだけが残る。

## 証拠: ドラフトの乖離6件（2026-08-06確認・廃止前に一旦改訂した際の記録）

ドラフトの最終更新は2026-07-18のコミット（`1907c36`）で、それ以降に確定した決定が一つも反映されていなかった:

1. **結線方式** — ドラフト「メッセージバスはSupabase Realtime(確定)」 vs [[monocore-bridge-polling-and-permission-model]]のポーリング化（2026-07-20撤回済み）。
2. **権限モデル** — 2ターン確認・ラチェット・事前固定操作の4点がドラフトに一切無かった。
3. **inbox廃止** — ドラフト「チャットが後継となるため廃止方向」 vs [[monocore-inbox-kept-for-now]]（廃止条件は投稿が自然にゼロになること）。
4. **Phase 1の価値** — ドラフト「実運用で確認済み」 vs 実際は疎通確認にすぎなかった（不使用判定自体は2026-08-06に撤回）。
5. **ページ構成** — `/projects`（プロジェクト板、[[morning-digest-page-in-monocore]]）と schedules の日別メモ欄・追加テーブル6本が未記載。「ページ数は1」のままだった。
6. **status行** — 全面凍結（2026-07-21）と解除（2026-08-06、[[monocore-third-pillar-of-ai-platform]]）、Phase 3の凍結理由（[[priority-pivot-autonomy-over-accessibility]]）が未記載。

**失われたもの（復元不能）**: [[priority-pivot-autonomy-over-accessibility]] は2026-07-20のPhase 3設計判断として「ポーリング化・ラチェット権限モデル・**3a/3b/3c分割**」の3点が「ドラフトに記録済み」と書いていたが、**3a/3b/3c分割の実体はドラフトにもengine内のどこにも存在しない**。前2件はノート本文から復元できたが、これだけは復元できなかった。**Phase 3相当（チャット窓口）に着手するとき、分割の議論はやり直しになる。**

## 棚卸しの結果（決まっていることの実際の姿）

ユーザーの見立て「ほとんど何も決まっていない」は半分正しい。正確には **決まっているのは「守るべき制約」で、決まっていないのは「何を作るか」**:

- **決定済みの制約は11件ある**（統合面はSupabaseスキーマ1つ／正の所在と導出物に手入力欄を作らない原則／Supabase維持・受信ポートゼロ／非同期が第一級／ポーリング／ラチェット式2ターン確認／合格判定は「使われ続けた」／inboxの廃止条件／replace系RPC禁止／DBに認証情報を置かない／ブリッジは薄く保つ）。
- **未決は8件**（次に何を作るか・チャット窓口の着手トリガー・参照リストの置き場・通知/PWAの要否・`board_mirror`の要否・AI編集マークの再開・音声の非画面トリガー・**taskboxの窓（エージェントセンター＝旧Phase 4構想）を作るか**）。

## How to apply

- **monocoreに「次はこれを作る」という表を作らない。** 作るものは実地の痛みから決める。`docs/design.md` §2は「決まっていない」ことを明示する欄であって、ロードマップに育てない。
- 制約（守るもの）と計画（作るもの）を同じ文書に混ぜない。混ざると、腐る側（計画）が腐らない側（制約）の信頼性まで下げる。
- 同型のリスクは他システムにもある — 実装が参照しない計画・目標の表を持つときは、当たった実績があるかを先に確認する。
