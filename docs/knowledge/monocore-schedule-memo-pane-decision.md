# monocore schedules に自由記述メモ欄を併設する判断

## 選択

monocore `/schedules` の各日セクション（DaySection）に、既存の予定欄と並べて**記法制約が一切ない自由記述メモ欄**を追加する。

- **PC（sm以上）は横並びで予定:メモ = 3:2**。当初Claudeは50:50を提案したが、ユーザーが3:2を指定した。
- **スマホは縦積み**（予定が上・メモが下）。横2分割は幅375pxでは両方とも実用に耐えないため。
- **テキストエリアの最低高を「3行相当(64px)」から「1行(24px) + 上下padding 8px = 40px」へ縮小**。これはメモ欄追加とセットの判断であり、ユーザー発案。

## 理由

**最低高の縮小はユーザーが提起した**。理由は「数か月先の予定を見るときのスクロールが今でも長く、メモ欄を縦に足すとさらに長くなるのは受け入れられない」。

実際に効く。空の日1件あたり（gap込み・スマホ）:

- 現状（予定のみ・最低64px）: 121px
- メモ縦積み・最低高そのまま: 186px（+54%）
- メモ縦積み・最低1行のみ（24px、余白なし）: 106px（−12%）
- **メモ縦積み・最低1行+py-2（40px）: 138px（+14%）← 採用**

未来2か月＝約60日はほぼ空なので、最低高を据え置くと約3,900px余計にスクロールすることになる。

**「最低1行・余白なし」を採らなかった理由**: 24pxのテキストエリアが縦に2つ隣接すると、スマホで予定欄とメモ欄を押し分けられない（タップ領域の推奨は44px前後）。押し間違えても記法警告が出ないので、「予定に書いたつもりがメモに入っていた」という無言の失敗になる。padding込みで40pxを確保する妥協案をClaudeが提案し、ユーザーが採用した。

## 併せて確認された設計判断

- メモは `schedule_day_notes` テーブル（1ユーザー・1ローカル日1行）へ upsert するだけとし、**予定側の保存経路（`replace_schedules_for_day` RPC + `schedule_day_revisions` のリビジョン競合検出）には一切触れない**。競合制御は inboxes と同じ last-write-wins。
- メモは `DayEntry` 型に入れず、`useDayNotes` フックが `Map<dayKey, string>` として独立管理する。`text-format.ts` / `sync.ts` とその既存テストへの波及をゼロにするため。

## 未着手として残っていること

スクロール長の**真因**は「空の日が空のまま場所を占めていること」で、最低高の調整はその緩和策にすぎない。抜本策（空の日の折りたたみ）は「どの日にもすぐ書ける」性質を壊すため今回は採らなかった。
