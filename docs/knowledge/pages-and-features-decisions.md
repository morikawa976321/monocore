# ページ・機能の実装判断

いつ読むか: monocoreの既存ページ・コンポーネントの経緯（なぜ今の形か、なぜ削除/追加したか）を確認するとき。

## インフラ方針: 束A(Supabase維持)+非同期AI対話（2026-07-14決定）

- monocore v2のインフラは**束A=Supabase現状維持**で確定。SQLite移行案は取り下げ、常時稼働ノード導入もなし。
- **人間と（ラップトップ上の）AIが非同期にやりとりする構造**を採用。スマホからのメッセージはSupabaseに溜まり、ラップトップ起床時にブリッジが処理・返信する。
- 理由（ユーザー明言）: 動機はデータ主権ではなく運用のシンプルさ。マネージドサービス維持が「何もしない」運用で最も認知負荷が低く、非同期化により「電車移動中にスマホから使いたい vs ラップトップは鞄内でスリープ」という制約衝突が実用上塞がる。リアルタイム性が必要な場面（自宅・研究室）ではラップトップは稼働している。
- UX確認（2026-07-16）: 外出中はチャットの返信が「ラップトップを次に開くまで来ない」体感になる仕様を、ユーザーが許容確認済み。
- 設計の正はmonocoreリポジトリの `docs/design.md`（2026-08-06更新。旧 `docs/monocore-v2-design-draft.md` は同日に廃止・分割）。このインフラ決定（束A・非同期構造）自体は現在も有効。

## schedulesへの自由記述メモ欄追加（2026-08-05判断）

monocore `/schedules` の各日セクション（DaySection）に、既存の予定欄と並べて記法制約が一切ない自由記述メモ欄を追加した。

- PC（sm以上）は横並びで**予定:メモ = 3:2**（Claudeは当初50:50を提案したが、ユーザーが3:2を指定）。
- スマホは縦積み（予定が上・メモが下）。横2分割は幅375pxでは両方とも実用に耐えないため。
- テキストエリアの最低高を「3行相当(64px)」から「1行(24px) + 上下padding 8px = 40px」へ縮小（ユーザー発案）。理由: 「数か月先の予定を見るときのスクロールが今でも長く、メモ欄を縦に足すとさらに長くなるのは受け入れられない」。

空の日1件あたり（gap込み・スマホ）の実測: 現状（予定のみ・最低64px）121px／メモ縦積み・最低高そのまま186px（+54%）／メモ縦積み・最低1行のみ(24px、余白なし)106px（−12%、ただしタップ領域が狭くなるため不採用）／**メモ縦積み・最低1行+py-2(40px) 138px（+14%）← 採用**。未来2か月＝約60日はほぼ空なので、最低高を据え置くと約3,900px余計にスクロールする計算だった。「最低1行・余白なし」を採らなかった理由: 24pxのテキストエリアが縦に2つ隣接すると、スマホで予定欄とメモ欄を押し分けられない（タップ領域の推奨は44px前後）。押し間違えても記法警告が出ないので、「予定に書いたつもりがメモに入っていた」という無言の失敗になる。

併せて確認された設計判断: メモは `schedule_day_notes` テーブル（1ユーザー・1ローカル日1行）へupsertするだけとし、予定側の保存経路（`replace_schedules_for_day` RPC + `schedule_day_revisions` のリビジョン競合検出）には一切触れない（競合制御はinboxesと同じlast-write-wins）。メモは `DayEntry` 型に入れず、`useDayNotes` フックが `Map<dayKey, string>` として独立管理する（`text-format.ts` / `sync.ts` とその既存テストへの波及をゼロにするため）。未着手: スクロール長の真因は「空の日が空のまま場所を占めていること」で、最低高の調整は緩和策にすぎない。抜本策（空の日の折りたたみ）は「どの日にもすぐ書ける」性質を壊すため今回は採らなかった。

### 実装時に踏んだReactの自動保存の罠（2026-08-05、QAレビューで検出）

このメモ欄実装で、型検査・テスト・lint・buildを全て通過した状態で潜んでいた実バグ2件。

**罠1: 未保存フラグをeffectの依存配列に入れるとデバウンスが壊れる。** `hasPendingChanges`（未保存ありフラグ）を、離脱時保存を登録する `useEffect` の依存配列に入れ、そのcleanupで `flush()` を呼んでいた。最初の1文字を入力した瞬間false→trueに変わり、effectが張り直され、そのcleanupがflushを呼ぶ。結果、500msのデバウンスが最初の入力では一切効かず即保存される（同じcleanupが他リソース＝予定・Inboxのflushも呼んでいたため、無関係な保存まで前倒しされていた）。対処: イベントハンドラ内から読む値はrefに逃がし、依存配列に入れない。リスナー登録のeffectは依存を安定させる。

**罠2: アンマウント時のクリーンアップはフックの定義順に走る。** カスタムフック内の `useEffect` クリーンアップで保留タイマーを `clearTimeout` するだけにし、保存自体は呼び出し側コンポーネントのcleanupに任せていた。Reactはアンマウント時、effectを定義した順（フック→コンポーネント本体）にクリーンアップを実行するため、フック側のcleanupが先にタイマーを消し、後から走る呼び出し側のflushは「保留中のタイマーが無い」と判断して何も保存しない。入力から500ms以内にSPA遷移すると内容が消える。対処: ライフサイクル保存の責務を1箇所に集約する（フック自身のアンマウントcleanupでflushまで行い、呼び出し側のcleanupからは外した）。

一般則: デバウンス保存は「保存経路の分岐（デバウンス満了／明示flush／失敗後の再試行／アンマウント）」ごとに、どの経路が保存対象を列挙するのかを1箇所で決めておかないと穴が開く。今回は「タイマーが張られている日」だけを列挙していたため、保存失敗でタイマーが消えた日が永久に再試行されない穴も同時に開いていた。

## Buttonコンポーネントのバリアント統一と見直し（2026-08-09〜11）

### 統一（2026-08-09、タスク `20260809-1430-monocore-button-unification`）

生の `<button>` 9箇所・6ファイルを `components/ui/Button` 経由に統一する際、`README-design.md` の棚卸しが挙げた4形すべてを実際に `color`/`size` のバリアントとしてButtonへ折り込んだ（「無理に寄せない」選択肢は取らなかった）。完了条件「`src`配下に生`<button>`+クラスが無い」が例外なしの絶対条件だったため、「寄せない」の意味は『Buttonを使わない』ではなく『既存の色トークンを無理に共有しない、専用のcolor/size値を新設してよい』と解釈した。

追加したバリアント: `color` に `ghost`（枠なし・hover背景のみ）/ `surface`（Card/Panel/FABと同じ「囲みの外枠」border-neutral-400/600トークン、primary/secondary/dangerとは別系統）/ `link`（下線テキストリンク）。`size` に `icon`(32px正方形) / `fab`(48px正方形) / `bar`(全幅左寄せ開閉バー) / `nav`(全幅左寄せナビ行) / `link`(テキストリンク用) を追加。

**訂正（2026-08-10）**: 当初「size 4種追加」と要約したが、実コードの `ButtonSize` は8/9時点から一貫して `'sm' | 'md' | 'icon' | 'fab' | 'bar' | 'nav' | 'link'` の**7値**（`link`の追加を書き漏らしていた）。「color 6値×size 6値」という要約が誤って流通した。バリアント数を参照するときは要約を鵜呑みにせず `Button.tsx` で数え直すこと。**正しい数は color 6値×size 7値。**

`surface`という新色を切った理由: FABは`border-neutral-400/600`だが、既存`secondary`は`border-neutral-600/500`で色が違う（`secondary`は他画面のボタン専用パレット、FABは`README-design.md`の「囲みの外枠」規定に属する別系統）。`secondary`を流用すると枠色が変わるため、`surface`として独立させた。`ref`もforward可能にした（React 19のref-as-prop。目次ドロワーのフォーカス復帰`tocTriggerRef`に必須）。

見た目が変わった箇所（すべて意図的・規約準拠が理由）: LoginClient送信ボタン（枠なし→primaryの2px枠、disabled不透明度40%→50%）、projects開閉バー（文字色がTertiary 700/300→Primary 900/50、README 2.1節「Tertiaryは主要操作ラベルに使うな」違反の是正）、DaySection元に戻すボタン（hover背景がneutral-300/700→200/800、README 3節のトークンと一致させた）、ThemeToggle（文字色neutral-600/400→700/300、600/400はREADMEのテキスト階層表に存在しない値だった）、DaySection・ThemeToggleのdark focus-visible ring（neutral-400固定→dark:neutral-600追加、指定漏れの是正）。いずれも新規デザイン判断ではなく既存規定と実装の食い違いの是正。見送ったものは無し（4形すべて折り込んだ）。ただし `nav` サイズは意図的にgap/レスポンシブ文字サイズをButton側に持たせず呼び出し側classNameに残した（SidebarActionButtonとThemeToggleでgap・文字サイズが実際に違うため）。

## デザイン文書と実装の食い違い（2026-08-09発見、要ユーザー判断のまま）

`README-design.md`（「絶対的な設計・実装ルール」と明記）3章は、カード等の通常状態ボーダーを `border-neutral-200` / dark `border-neutral-800`（Default）、フォーカス/アクティブ状態を `border-neutral-400` / dark `border-neutral-600`（Focus/Active）と2段階で規定している。しかし既存の（このタスクで書いていない）コンポーネント（`ProjectSection.tsx` の `CollapsedProjectCard`、`projects/page.tsx` の空状態メッセージボックス、`Sidebar.tsx` のモバイルハンバーガーボタン）は、フォーカス/アクティブ状態でない通常のカード・ボックスに一貫して `neutral-400/600` を使っている。

`/reports`実装のQA（cursor-agent `gpt-5.6-sol-high`）で2回連続、文書の字面通り `200/800` へ直すよう指摘されたが、既存コンポーネントとの視覚的一貫性を優先し `400/600` のまま据え置いた（このページだけ境界線が薄くなると、かえってアプリ全体で見て不統一になるため）。

位置づけ: これは「AIが良かれと思って独自解釈した」のではなく、文書と実装のどちらを正とするかという、本来ユーザーが決めるべき食い違い。今回は単一機能追加のタスク内で全既存コンポーネントを書き換える権限も範囲も無かったため、既存実装への追随を選んだ。**未解決のまま残っている論点**: `README-design.md`の記述を実態(`400/600`)に合わせて更新するか、既存コンポーネント側を文書(`200/800`)に合わせて直すか。後者を選ぶ場合は`/reports`だけでなく`ProjectCard`・`Sidebar`等を含む横断的なクリーンアップタスクになる。（`README-design.md` 3章 / `AGENTS.md` の同等記述を参照）

示唆: knowledgeが空になった原因は「使われなかった」ではなく、レコード型CRUD（title/body/status/並び順）の入力コストが、単一テキストエリアへの追記に負けた可能性が高い（「入力が面倒でサボる」という以前からの申告と整合）。

決定間の緊張（2026-08-06に解消可能な状態へ変化）: 発見当時は「人間向けの面はmonocoreに一本化」（2026-07-14決定）と「monocoreは全面凍結」（2026-07-21〜08-06）が同時に有効で、人間が常時読む静的リストの正しい置き場が制度上どこにも無かった。当時のinbox同居は規律の失敗ではなくこの2決定の論理的帰結。凍結は2026-08-06に解除されたため、これは「実装で解ける未決問題」に変わったが、**参照リストの面を作るか既製ツールへ出すかは未決のまま**残っている。

なぜ起きたか: 責務境界を「情報の寿命軸」「読者軸（AI向け/人間向け）」で切っていたが、この領域では「実装余力があるか」という第3の制約が効いており、寿命・読者だけでは行き先が決まらない。inboxの整理を設計するときは、参照リストの行き先を先に決める（凍結を部分解除して面を作るか、この種の純参照リストだけAI活用基盤の外の既製ツールへ出すか）。決めずに仕分けを始めると、参照リストだけが必ずinboxに残る。

## inboxパネルは当面維持（2026-07-20判断）

Phase 3（チャット窓口、後に凍結）に進む/進まないに関わらず、inboxパネルはしばらく残す判断。

理由: 設計ドラフトはinboxを「チャットが後継となるため廃止方向」としPhase 3での廃止を予定していたが、inboxは**ブリッジ（ラップトップ）が寝ている間に成立する唯一のモバイル書き込み経路**である。したがって廃止判定はPhase 3出荷時点ではなく、チャットが睡眠中の捕捉をどこまで代替できたか観測した後に後ろ倒しすべきと判断した。廃止の条件は「チャットが実装された」ではなく「**inboxへの投稿が自然にゼロになった**」こと。

## /newsは面を増やす基準（観察判定）を要さない（2026-08-14判断）

monocoreの面を増やす基準は「動いた」ではなく「使われ続けた」（`docs/design.md` 制約10。作って使われず消した面が過去に4つある）。当初は `/news` についても「移行の1〜2週間後に実際に開いたかを確認する」という観察判定を未決のまま残していた。

本人は2026-08-14、「**/newsは必ず使うのが確定しているので問題ない**」と回答し、観察による判定は行わないことになった。

理由: 過去に消えた4面（旧projects/tasks/knowledge/要注意タスクパネル）は新規に作った面で、使うかどうかが仮説だった。`/news` は違い、**移行前からLAN内のFlaskで毎日読んでいたものの移設**であり、「作ったが使われない」リスクではなく「読む場所が変わるだけ」で判定対象の不確実性がそもそも無い。

一般化: 面を増やす基準が効くのは「新しい習慣を仮定する面」であって、既存の習慣の置き場を移すだけの面には効かない。
