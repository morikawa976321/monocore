# デバウンス自動保存で踏んだ罠（React）

monocoreのメモ欄実装（[[monocore-schedule-memo-pane-decision]]）で、QAレビューが検出した実バグ2件。いずれも型検査・テスト・lint・buildを全て通過した状態で潜んでいた。

## 罠1: 未保存フラグをeffectの依存配列に入れるとデバウンスが壊れる

`hasPendingChanges`（未保存ありフラグ）を、離脱時保存を登録する `useEffect` の依存配列に入れ、そのcleanupで `flush()` を呼んでいた。

最初の1文字を入力した瞬間 false→true に変わり、**effectが張り直され、そのcleanupがflushを呼ぶ**。結果、500msのデバウンスが最初の入力では一切効かず即保存される。同じcleanupが他リソース（予定・Inbox）のflushも呼んでいたため、無関係な保存まで前倒しされていた。

**対処**: イベントハンドラ内から読む値はrefに逃がし、依存配列に入れない。リスナー登録のeffectは依存を安定させる。

## 罠2: アンマウント時のクリーンアップはフックの定義順に走る

カスタムフック内の `useEffect` クリーンアップで保留タイマーを `clearTimeout` するだけにし、保存自体は呼び出し側コンポーネントのcleanupに任せていた。

Reactはアンマウント時、**effectを定義した順（フック→コンポーネント本体）にクリーンアップを実行する**。フックはコンポーネント冒頭で呼ばれるので、フック側のcleanupが先にタイマーを消し、後から走る呼び出し側のflushは「保留中のタイマーが無い」と判断して何も保存しない。入力から500ms以内にSPA遷移すると内容が消える。

**対処**: ライフサイクル保存の責務を1箇所に集約する。フック自身のアンマウントcleanupでflushまで行い、呼び出し側のcleanupからは外した。

## 教訓

デバウンス保存は「保存経路の分岐（デバウンス満了 / 明示flush / 失敗後の再試行 / アンマウント）」ごとに、**どの経路が保存対象を列挙するのか**を1箇所で決めておかないと穴が開く。今回は「タイマーが張られている日」だけを列挙していたため、保存失敗でタイマーが消えた日が永久に再試行されない穴も同時に開いていた。
