# リモートDBへの `db push` はAIセッションからは通らない（2026-08-12実測）

## 事実

カードの2欄改名（[[card-fields-time-axis-not-actor]]）で `npx supabase db push --linked --yes` を実行しようとしたところ、**自動許可モードのゲートに拒否された**。Bashツール・PowerShellツールの両方で同じ結果で、本人が事前に計画を承認していても変わらなかった。ローカルへの `supabase migration up` は通る。

## 段取りへの含意

**リモートのスキーマ変更を含む作業は、「本人が1コマンド打つ」工程が必ず途中に挟まる前提で組む。** AIが一気通貫で終えられるのはローカル適用とコード・文書までである。したがって:

- **リモート適用より後にしか検証できないこと**（本番での実データ確認・投入スクリプトの実走）を、完了条件の中に混ぜない。混ぜると作業が本人待ちで宙吊りになる。
- 適用前後で**壊れる向き**を先に確かめておく。列のRENAMEなら「DBが新・アプリが旧」でも「DBが旧・アプリが新」でも画面は落ちるので、**本人へ渡す指示にはコマンドだけでなく順序**（適用 → デプロイ）を書く。
- 無人drainが同じ時間帯に走るなら、**失敗しても安全な失敗の仕方**を申し送りに書いておく（今回は「upsertが列不在で落ちたら `PROJECT_BOARD_CHECKED` を出さずに終われば基準SHAが進まず次の枠が再試行する」）。

既存の [[monocore-remote-migration-drift-fixed]] は「pushの前に差分を確認する」という教訓だが、本ノートは**そもそもAI側がpushできない**という前段の制約を記録する。taskbox の `resume_when_http_200`（リモート未適用のテーブルをHTTP GETで検知してqueueへ自動復帰させる仕組み）は、この制約に対する既存の対処である。
