# 「疎通確認」が破壊的操作だった事故

2026-07-17のmonocore M1で、新設したservice_role専用RPC `replace_schedules_for_day_as` の**GRANTが効いているかを確認する**目的で、`p_items=[]`(空配列)を渡して呼んだ。このRPCは「その日を丸ごと置換する」仕様のため、**対象日(JST 2026-07-20)に実在したユーザーの予定2件(大学の講義)が削除された**。dead tupleから復元して原状復帰できたが、バックアップは無く、VACUUMが走っていたら永久に失われていた。

## 何を間違えたか

- 「権限が通るか」だけを見ていて、**その呼び出しが持つ副作用(全削除→再挿入)を意識から外していた**。
- 対象日が空かどうかを**確認しなかった**。直前に「2026-07-18は空」と確認したのに、別の日(07-20)を無検証で選んだ。
- 読み取り専用で確認する手段(`pg_proc.proacl` を見る、`SET ROLE` してEXECUTE権限だけ試す)があったのに、実際に副作用のある呼び出しをしてしまった。

## 次回への規則

1. **破壊的操作を含む関数の疎通確認は、副作用の無い方法で行う**(ACLはカタログを読めば分かる。権限テストは `SET ROLE` + 権限エラーの有無で判定できる)。
2. どうしても実呼び出しが要るなら、**対象が空であることを直前に確認**してから叩く。
3. 破壊的操作の前に**指紋(件数+id列のmd5)を取る**。原状復帰を証明でき、事故にも即座に気づける。
4. 「置換(replace)」「同期(sync)」「upsert」系のAPIは、**引数が空=全削除**を意味しがち。空入力は最も危険な入力として扱う。
