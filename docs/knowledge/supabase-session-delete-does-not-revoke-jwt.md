monocoreの無限リトライ障害([[schedule-revision-conflict-retry-storm]])で、暴走しているクライアントを止めようとして得た知見。

**効かなかった手**: `delete from auth.sessions;`(全セッション削除)。`auth.sessions` が制御するのは**トークンのrefreshだけ**で、`auth.uid()` はJWTのクレームから直接読まれる。発行済みアクセストークンは有効期限(既定3600秒、Supabaseは最大1週間まで設定可)まで通り続けるため、削除しても即座には止まらない。

**JWT secretのローテーション**は全トークンを即失効させられるが、**旧形式(`eyJ...`)のanon/service_roleキーは同じsecretで署名されたJWT**なので巻き添えで失効する。monocoreのremote service_keyは旧形式のため、Vercel環境変数・scraper設定・skillの `config.json` を全部更新する必要が生じる。新形式(`sb_publishable_*` / `sb_secret_*`)ならこの巻き添えは無い。

**実際に効いた手**: **サーバ側を書き換えてリクエストを成功させる**。楽観ロックの `expected 11 / current 17` で弾かれ続けていたので、`update schedule_day_revisions set revision = 11 where day_key = '2026-08-29';` でサーバをクライアントの期待値に合わせた。次の1回で保存が成功し、クライアントの `dirty` フラグが解除されて**数秒で停止**した。関数もキーもスキーマも触らない。

**一般化**: 失敗し続けて暴走しているクライアントを外から止めるとき、「認可を奪う」は遅く、「**期待どおりの成功を1回返してやる**」が速い。ただし成功させる以上、そのクライアントが送っていたペイロードが実際に書き込まれる。今回はそれが**空の予定表**で、対象日の既存データが消えた。実行前に対象データを退避すること。

**2026-09-02の再発で分かったこの手の限界**: **期待値を正確に当てないと効かない**（ユーザーが `revision` を50へ戻したが暴走側の期待値は53だったため止まらなかった）。さらに巻き戻した値は、**過去にその値を読んだ古いクライアントと偶然一致して古い内容で上書きされる**新たな経路を作る（対処は、止血後に過去の最大値より上へ戻すこと）。**より確実なのは、そもそも競合で例外を投げないようRPCを書き換えること** — 書き込まずに戻り値で競合を返せば、エラーログが出ないので暴走を放置しても害が出ず、暴走側も「成功」と読んで自分から止まる。monocoreは migration `20260902001000` でこれを入れ、この状況自体が起きなくなった（[[client-side-guard-cannot-reach-the-runaway-client]]）。

**判定に使う指標**: CPUグラフは1時間バケットで遅れるので停止判定に使えない。**ログのエラー行が今も流れているか**だけが指標になる。
