# monocore v2 設計ドラフト — AI活用基盤の唯一のユーザー窓口

status: 方針確定(2026-07-14)。M1をtaskboxに登録済み(2026-07-16、実装はcursor-agent多用のユーザー指示付き)

## 0. 前提となる決定事項(2026-07-14確定)

1. **context-engine(記憶系)・taskbox(実行系)は現状維持。** ユーザーはこの2システムに直接触らない。
2. **ユーザーがAI活用基盤の恩恵を受けるためのすべての窓口を monocore に集約する。** monocoreの大幅な発展・肥大化を許容する。
3. **インフラは束A=Supabase現状維持で確定。** SQLite移行・常時稼働ノードは取り下げ(動機=運用のシンプルさに照らした判断。経緯は§7論点1)。
4. **人間とラップトップ上のAIが「非同期に」やりとりする構造を採用。** チャットはリアルタイムを保証しない。スマホからのメッセージはSupabaseに溜まり、ラップトップ起床時にブリッジが処理・返信する(taskboxと同じ非同期哲学)。AIはクラウドLLM(Claude)・ローカルLLM(llama-server)のいずれもブリッジ側で選択可能とする(multi-ai-delegationの枠組みと整合)。

補助的な前提(過去の決定・事実):

- 責務境界は「寿命」と「読者」の2軸で定義する: engine=AIが読む永続文脈 / monocore=**人間が読む生きたデータ** / taskbox=AIが実行するジョブ列。
- monocoreの現行資産: スケジュール(毎日使用・行テキストUX)、タスク(2項目クイック入力)、プロジェクト/ナレッジ(Markdownカード)、モバイル最適化、Supabase(RLS・マジックリンク認証)、RasPiバックアップ。
- 現行の弱点: AIからの書き込み経路がない / カテゴリー間連携ゼロ / 通知ゼロ / インボックスは出口のない単一テキストblob。
- monarcsの教訓: 実装コストがコアバリューを上回った時点で畳む。**ビッグバン開発をせず、各フェーズ単独で価値が出る順に積む。**
- フロントUI要件(2026-07-08): 場所・デバイス・入力方法の3自由度 / チャット基調+補助UI / 音声入力必須 / 音声トグルの画面操作は嫌悪(非画面トリガー志向)。

## 1. 結合方針 — 「直接結合ゼロ、すべてAI(ブリッジ)経由」

**3システムは互いを知らない。** 結合はすべて、ローカルPC上のブリッジ(=AIエージェントの実行主体)が担う。

```
依存グラフ:
  taskbox ──→ engine          (既存・不変)
  bridge  ──→ engine / taskbox / monocore(API)
  monocore ──→ (どこも参照しない)
  engine  ──→ (どこも参照しない)
```

- monocoreはengine/taskboxのファイルを読まない。engine/taskboxはmonocoreを知らない。
- **統合面はmonocoreのSupabaseスキーマただ1つ**(テーブル+RLS+service roleの契約)。engine/taskboxの形式が変わってもブリッジだけ直せばよく、逆にmonocoreを将来別物に置き換えてもengine/taskboxは無傷。「engineだけが不可侵のコア、実行系・表示系は交換可能」の原則を保つ。
- taskboxの状態をmonocoreで見せる場合も、monocoreが持つのは**ブリッジが書き込む読み取り専用の写像(ミラー)**であり、正は常にtaskbox側のmd。

## 2. アーキテクチャ全体像

```
[ユーザー: スマホ/PCブラウザ]
        │ HTTPS + Supabase Auth(マジックリンク)
        ▼
[monocore Web (Next.js) + Supabase (Postgres / Realtime / Auth)]
        ▲ アウトバウンドWebSocket(Realtime購読) + service roleでのCRUD
        │
[bridge: Windows PC常駐の薄いデーモン]
   ├─ チャット受信 → Claude(Agent SDK / claude -p)セッションを起動
   │     └ 起動プロトコル通りengineをマウント、taskbox/monocoreをツールとして操作
   ├─ taskbox board・handoverの変化を検知 → ミラー/意思決定カード/通知をmonocoreへpush
   └─ 定時ジョブ(朝のブリーフィング生成など)
```

要点:

- **メッセージバスはSupabase Realtime(確定)**。monocoreのDBに`messages`を書き、ブリッジが購読して応答を書き戻す。PCからはアウトバウンド接続のみで**受信ポートを一切開けない**。Cloudflare Tunnelは不要(2026-07-08のTunnel再利用決定を改訂)。
- **非同期が第一級の設計原則(確定)**。ブリッジ停止中(ラップトップスリープ)もメッセージ投稿・データCRUDは常時成立し、ブリッジ起床時に未処理メッセージを順次処理する。UIは「送信済み/処理中/返信あり」の状態を明示し、即答を約束しない。ブリッジ起動時のキャッチアップ処理(未処理分の一括消化)を必須要件とする。
- **モデルルーティング**: ブリッジはメッセージの性質に応じてクラウドLLM(Claude session)・ローカルLLM(llama-server)を選択できる構造とする(初期実装はClaude固定でよい)。
- ブリッジは「薄く」保つ。エージェント機能は既存のClaude(スキル・taskboxプロトコル)をそのまま使い、ブリッジは配送と写像だけを行う。monarcsの二の舞(自前エージェント基盤の肥大化)を避ける。
- チャット経由のセッションも通常のClaudeセッションと同格: engineを読み、メモ魔方針でengineに記録し、必要ならtaskboxに積む。**ユーザーはmonocoreのチャットに話すだけで2システムの恩恵を受ける。**

## 3. データモデル拡張(Supabase)

既存テーブルへの変更:

- 全リソーステーブルに `updated_by TEXT ('user'|'agent')` を追加(AI編集の監査可能性)。
- 楽観ロック: ブリッジ側の書き込みは read→modify→write を1操作で行い、`updated_at`不一致時は再読込(2026-03-25の2デバイス編集バグと同種の競合対策)。

新規テーブル:

| テーブル | 役割 | 正の所在 |
|---|---|---|
| `messages` | チャット(id, role: user/agent/system, content, thread_id, created_at, status) | monocore |
| `decision_cards` | 意思決定カード(question, options jsonb, recommendation, status, answer, source_ref) | monocore(回答)/taskbox(発生源) |
| `board_mirror` | taskboxのqueue/running/done/failedの写像(task_slug, state, summary, updated_at) | **taskbox**(ミラーは読み取り専用) |
| `notifications` | 通知(kind, title, body, read_at) | monocore |

インボックス(単一blob)は**チャットが後継**となるため廃止方向(既存内容はAIで排出してから)。

## 4. 機能要件(フェーズ順・各フェーズ単独で価値が出る)

### Phase 1 — AI編集権(UI変更なし・最小工事)
- ブリッジ以前の暫定として、ローカルClaudeセッションからservice keyでmonocore DBをCRUDできる**スキル1本**を作る。
- 対象: schedules(既存RPC `replace_schedules_for_day` 流用可)・tasks・knowledge(projectsは2026-07-17に廃止・削除)。
- 価値: 「明日14時に歯医者」「読みたい本に追加」が会話で済む。リストの鮮度スパイラルが逆回転を始める。

### Phase 2 — 毎日の面への集約(小工事)
- スケジュール画面に「今日期限・期限切れタスク」を差し込み表示(FK不要、クエリ1本)。
- `updated_by` 表示(AIが触った項目の識別)。
- 価値: 通知機能の不在を、毎日見る唯一の面への集約で代替。

### Phase 3 — チャット窓口(本丸)
- グローバルなチャットパネル(全ページからスライドオーバー、モバイルは全画面)。
- `messages` + Realtime + ブリッジ常駐 + Claude Agent SDKセッション。
- 音声入力: まずブラウザ標準(Web Speech API)のプッシュトゥトーク。非画面トリガー(イヤホンボタン等)は追って検討(→§7論点3)。
- 価値: 3自由度(場所・デバイス・入力方法)の達成。monarcsコアバリュー3の回収。インボックス廃止。

### Phase 4 — エージェントセンター(taskboxの窓)
- `/agent` ページ: board_mirror表示、意思決定カード(handoverのブロック項目をブリッジがカード化→ユーザーがタップ回答→ブリッジがtaskboxへ書き戻し・queue昇格)、AI変更履歴、通知一覧。
- PWA化+Web Push(drain完了・失敗・判断待ちをスマホに通知)。
- 価値: 「AIの仕事を眺めて、詰まりだけ解消する」運用がスマホで完結。ai-delegation-strategyの意思決定カード構想の実装先。

### スコープ外(明示)
- 資産・家計(資産計画.xlsxの運用で確定済み。将来ブリッジ経由の閲覧を検討する余地はあるが今は触らない)
- 外部カレンダー同期・多ユーザー対応

## 6. セキュリティ要件

- service key・ブリッジ資格情報はローカルPCのみに置く(クライアント・リポジトリに置かない)。
- チャットは実質「自宅PC上のエージェントへの遠隔入力」なので、Supabase Authの単一ユーザー制限を厳格に(既存RLS+許可メールアドレスの固定)。
- ブリッジ経由セッションの権限は通常セッションと同等に留め、破壊的操作はチャット上の確認を挟む。
- engine/taskboxのローカルgit・非公開原則(pushしない)は不変。

## 7. 未決の論点

### 論点1(最大): インフラ束の選択 — クラウド束 vs ローカル束 【決着済み: 束Aでfix(2026-07-14)】

以下は検討経緯の記録。結論: **束A(Supabase維持)+非同期対話構造**で確定。判断軸は「構成図のシンプルさ」ではなく「運用のシンプルさ(=ユーザーが日々払う注意の量)」であり、マネージドサービス維持が最小。モバイル利用(スケジュール面)は維持され、チャットの非同期化によりラップトップスリープ中の穴を塞ぐ。

到達経路・DB・ホスティングは独立には決められず、整合する2束のどちらかを選ぶ(2026-07-14議論)。

| | **束A: クラウド** | **束B: ローカル(SQLite移行)** |
|---|---|---|
| DB | Supabase(現状維持) | ローカルSQLite |
| Web | クラウドホスティング | 自宅PCでNext.jsを常駐 |
| 到達経路 | 不要(Realtimeバス、受信ポート開放なし) | **Cloudflare Tunnel等が実質必須** |
| 認証 | Supabase Auth(現状) | 自前 or Cloudflare Access(Tunnel側で認証) |
| ブリッジ | Realtime購読(ネットワーク越し) | 同一マシン内で完結(最も単純) |
| 可用性 | PCと無関係に24/7 | **PCの稼働時間に従属**(スリープ・再起動=停止) |
| データ主権 | 個人データがクラウドに残る | engine/taskboxと同じローカル完結・push禁止方針に整合 |
| 移行コスト | ゼロ | DB層書き換え+認証再実装+常時稼働運用の確立 |

- 束Bはユーザーの既存方針(ローカルgit限定・データ主権)と哲学的に一貫する。最大の代償は可用性で、毎日使うスケジュール面がPC稼働に従属する点をどう許容/緩和するかが判断軸。
- Phase 1〜2はどちらの束でも同一実装(DB抽象を1層挟む)。束の決定はPhase 3着手までにあればよく、フェーズ進行をブロックしない。

#### 追記(2026-07-14): 「電車問題」と常時稼働ノード

制約の追加: ユーザーはラップトップ一本化の方向であり、**電車移動中(ラップトップは鞄でスリープ)にスマホからmonocoreを使いたい**。この要件で束の分析が変わる。

- 束B(SQLiteをラップトップに置く)は電車内で全滅する。
- 束A(Supabase)でもデータCRUDは動くが、**AIチャットはブリッジ=ラップトップが寝ている限り死ぬ**。つまり「いつでもどこでもフルのmonocore」は、DB選択と無関係に**常時稼働ノードなしでは成立しない**(engine/taskboxがブリッジ所在地を規定するため、ブリッジをクラウドに逃がすことはできない)。

電車内で何が動くかの整理:

| 構成 | 予定を見る | 追加・編集 | AIチャット |
|---|---|---|---|
| B: SQLite on ラップトップ | ✗(PWAキャッシュで△) | ✗(書込キューで△) | ✗ |
| A: Supabaseクラウド | ✓ | ✓ | ✗ |
| **C: 常時稼働ノード(自宅の母艦)** | ✓ | ✓ | ✓ |

**束C = 自宅に常時稼働の小型ノード(N100級ミニPC等)を1台置き、engine・taskbox・monocore(SQLite+Next.js+ブリッジ)をすべてそこへ移す。ラップトップは開発・閲覧クライアントに退く。** Tunnel+Cloudflare Accessで到達。データ主権(束Bの利点)と24/7可用性(束Aの利点)を両立する唯一の構成。夜間drainのcronがラップトップのスリープに脅かされる既存の脆弱性も同時に解消する。代償: デバイス+1(ただし持ち歩かない自宅インフラ)、初期セットアップ、ノード障害点の管理。

過渡案: 束Aを維持したままPhase 1〜3を進め、束Cのノード導入をもって SQLite移行+engine/taskbox移設を一括で行う(移行は1回で済ませる)。

#### 追記2(2026-07-14): 動機の確定により選択肢が2つに絞られた

ユーザーの明言: インフラ選択の動機は**ハードウェア構成と接続のシンプル化**であり、データ主権ではない。この動機の下では:

- 束C(常時稼働ノード)は動機に反する(ハードウェア+1)。データ主権が動機でない以上、束Cを選ぶ理由が消える。
- 束B(SQLite+Tunnel)も動機に反する(Tunnel・Access・常時稼働運用という接続の複雑さを自前で抱え込む)。
- 残る選択肢は2つ:
  - **束A(Supabase現状維持)**: 追加ハードウェアゼロ。接続は「ブラウザ→Supabase」1本(運用実績あり)。モバイルのデータCRUDは24/7。チャットはラップトップ稼働中のみリアルタイム、スリープ中は**非同期**(メッセージがDBに溜まり、起床後にブリッジが処理して返信)として成立する。
  - **束D(完全ローカルアプリ化)**: monocoreをラップトップ専用ツールと再定義。SQLite+localhost、認証・Tunnel・クラウドすべて不要で構成は極限までシンプル。**代償はモバイル利用の全面放棄**(毎日使っているスケジュール面のモバイル導線、3自由度要件、Phase 4の外出先での意思決定カードを全て失う)。

判断軸はただ1つ: **スマホからのmonocore利用(特にスケジュール)を捨てられるか**。捨てられないなら束Aが簡素化の最適解であり、SQLite移行はむしろ複雑化になるため取り下げ。捨てられるなら束Dが一貫する。

## 8. 完成イメージ(2026-07-14すり合わせ)

### 8.1 ユーザー体験 — 完成したmonocoreのある1日

- **朝(スマホ・PWA)**: monocoreを開くとスケジュール面。今日の予定の隣に期限タスクが差し込まれ、ヘッダに判断待ちカード2件のバッジ。チャットには前夜のdrain完了報告と朝のブリーフィングが届いている。
- **電車(ラップトップは鞄でスリープ)**: 予定の確認・編集、タスク追加は普通に動く(データはSupabaseで24/7)。思いつきを音声かフリックでチャットに投げると「受付済み・処理待ち」と表示される。判断待ちカードに選択肢タップで回答する。即答は期待しないし、待たされもしない。
- **研究室(ラップトップを開く)**: ブリッジが起床し、溜まったメッセージを順に消化。「読みたい本に○○追加」→ knowledgeのリストが更新され(AI編集マーク付き)返信が届く。研究アイデアのつぶやき → engineに記録された旨の返信。電車で回答したカード → taskboxへ書き戻され、タスクがqueueに昇格。
- **夜(スマホ)**: プッシュ通知「タスクX完了」。/agentを開くと成果物へのポインタ、board写像、今日AIが触った項目の変更履歴が見える。
- **総括**: ユーザーはmdファイル群・ターミナル・Supabase管理画面を一切開かない(開発作業を除く)。生活のすべての接点はmonocore。リストはAIが会話から更新し続けるため常に新鮮で、「読みに行く価値」が維持される。書く手間は「話す」まで下がる。

### 8.2 システム設計 — 完成時の構造

```
[ブラウザ/PWA] ←HTTPS→ [Supabase: Postgres+Realtime+Auth]  … 統合面(唯一の契約)
                              ↑ アウトバウンドのみ
[bridge(ラップトップ常駐)] ─→ Claude(Agent SDK) / llama-server をルーティング
        ├─→ engine(md, 読み書き=メモ魔・文脈読解)
        ├─→ taskbox(md, enqueue・handover・写像抽出)
        └─→ monocore DB(service key, CRUD+写像push)
```

- **不変条件**: ①3システムは互いを知らない(全部知るのはブリッジだけ) ②正の所在は 人間データ=monocore / 実行状態=taskbox / 永続文脈=engine で、monocore内のboard_mirror等は使い捨ての写像 ③受信ポートゼロ・service keyはラップトップの外に出ない ④AI書き込みは全件updated_by監査+楽観ロック ⑤非同期が第一級(ブリッジ停止中も受付は止まらない)
- **メッセージのライフサイクル**: user投稿(pending) → ブリッジ取得(processing) → AIセッション実行(engine読解→行動→返信) → replied。ブリッジ起動時は未処理分を古い順にキャッチアップ。
- **意思決定カードのライフサイクル**: taskbox handoverのブロック項目をブリッジがカード化 → ユーザー回答 → ブリッジがhandover更新・queue昇格 → カードclose。
- **障害の性質**: ブリッジが死んでも失われるものはない(メッセージ・回答はDBに残り、次回起床で消化)。drainと同じ冪等・非同期パターン。
